# Check specification (rules 0.2.0)

Every scripted check the plugin ships is defined here. The code in `plugin/server/src/checks/` implements this table exactly; `docs/checks.md` is generated from the code for users.

## How to read the tables

- **Unit**: what the check counts. It returns one result (pass or fail) per unit and nothing for anything else. The score uses the pass rate over units.
- **Fails when**: the condition for a `fail` result. Everything else in the unit set is a `pass`.
- **Sev / W**: severity and weight. Weight 0 means the check never changes the score; those are `info` checks based on rules of thumb.
- **Conf**: `confirmed` is a measured fact. `likely` is a strong signal that can have a legitimate exception.
- **Needs**: capabilities the audit must provide. The crawl provides `full_crawl`, `sitemap` and `robots`, and `live_site` when the site is not on this machine (`options.local` is not `true`); the external link check provides `outbound`; the check of image files (media module) provides `image_files`; the check of sharing images (smo module) provides `social_images`; the read of the app association files (aso module) provides `app_files`; the read of `/llms.txt` (ai module) provides `llms_txt`; the crawl provides `ai_robots` when it recorded what robots.txt tells AI crawlers (`CrawlResult.ai_robots`) and `ai_pages` when its records carry the ai module's page signals (rule set 0.2.0 and later); the Core Web Vitals measurement provides `lab_data` and `field_data`. The engine skips the check otherwise, with the reason the collector gave.
- **Doc**: key into the reference list at the end.

Terms:

- *html page*: a record with status 200 and `is_html` (`ctx.htmlPages`).
- *indexable page*: a record with `indexability.indexable` (`ctx.indexablePages`).
- *effective canonical*: an entry in `page.canonicals` with `in_head: true` and a non-null `url`.
- *names the page itself*: a canonical URL equal to the page URL once the escapes of `!`, `'`, `(`, `)` and `*` are decoded (`sameCanonicalTarget`). Browsers send these characters as they are written, so a page linked as `/Today's_article` with a canonical to `/Today%27s_article` names itself; RFC 3986 does not make the two forms equal, so `normalizeUrl` keeps them apart (it decodes the escapes of unreserved characters only, so `%7E` and `~` are one URL). `canonical_elsewhere` and `seo.canonical.target_not_ok` use this comparison.
- *noindex*: `indexability.reasons` contains `noindex_meta` or `noindex_header`.
- *could not read*: `isUnverifiable(record)` is true. The site's firewall challenged the crawler, the site rate-limited it, or a redirect led to a URL that robots.txt disallows. That says something about the audit and nothing about the site, so such a record is never a unit and never a broken target.
- *start page*: `ctx.resolve(crawl.start_url)`.
- *tested page*: an entry of `ctx.vitals.pages`, one of the few pages whose Core Web Vitals were measured.

Evidence strings taken from a page are clipped with `clip()`. `related_urls` are sorted. `evidence.limit`, when present, is a short sentence of the plugin's own on what the measurement cannot see (for every ai finding judged from robots.txt: that a CDN or firewall can treat the real crawler differently); it is kept apart from `detail`, so the 300-character clip of the tool output and the report never cuts it.

## Source files (repo mode)

A finding can carry `source: {file, line, route}`: the file of the user's project that the finding comes from. It is added after the checks ran, by `repo/sources.js` (ARCHITECTURE.md 4.12), only in an audit that was given a source folder, and only where the file can be determined. It is not part of a check's result, of the finding id or of the score, so the same crawl gives the same ids with and without it.

- `file`: path relative to the project folder.
- `line`: the line of the element in `file`, or null. Given for HTML files only.
- `route`: the Next.js route (`/blog/[slug]`) or the URL path.

No source is given to a site-level finding without a URL, to `seo.https.site_not_https`, `seo.https.not_enforced` and `seo.cwv.*` (they are about the server or about Google's measurements), or to a finding whose URL no file of the project answers. In a Next.js project that includes a URL that redirected or answered 404, and a URL that only a route with a dynamic segment matches unless it answered 200.

## Which hosts are the site

Every rule that asks whether a host is the audited site asks `util/site-identity.js` (since rule set 0.1.8; before, eight modules each had a rule of their own and disagreed on a trailing dot, a port and a sister domain). The module answers four questions per crawl:

- *Internal*: a page of the site as the crawl scopes it (`isInternalUrl`): the same host without a leading `www.`, on the same port, whatever the scheme; subdomains only with `include_subdomains`. The host written with a trailing dot is not internal, so that the crawl does not read every page a second time under another address.
- *Site host* (`hostName`): the host's name in lower case without the port, one trailing dot or a leading `www.`. It decides the one-crawl-per-site rule (`crawlKey`; for a site on this machine, the port), `seo.canonical.cross_host`, and the share links of the site.
- *Same organisation*: a host the site's owner holds. Its name is the site's or, for a local crawl, the deployed site's; or it has the same *registered domain*, the public suffix and one label more (`acme.co.uk` for shop.acme.co.uk), with the public suffixes taken from the Public Suffix List; or it has the site's name under another ending (acme.de for acme.com) and a visible link on some crawled html page goes to that registered domain. Anyone can register `<name>.<ending>`, so before rule set 0.1.8 a spammer's acme.xyz passed as acme.com's own; now it is another site unless the site links to it where visitors see it. An IP address and a name of one label have no registered domain and match only themselves. The security scan of one page knows only that page, so it records links to sister domains and the hidden-link check decides with the visible links of every page.
- *Deployed*: for a local crawl told its deployed address, a URL on that address's host name, whatever the scheme or port. Nothing is ever requested there.
- *Public*: a host that can be a public site (not this machine, not a private address, not a local-network name, not a single label), which is the only kind Core Web Vitals name to Google.

**Public suffixes.** The list is read from `plugin/server/data/public-suffixes.txt`, a compact copy of the Public Suffix List (https://publicsuffix.org/list/public_suffix_list.dat, VERSION 2026-11-13_14-44-35_UTC since rule set 0.1.9, which added six hosting rules to the copy of 2026-11-12, both the ICANN section, with endings such as `me.uk`, `gen.tr`, `web.tr` and `id.au`, and the private section, with hosting domains that give each customer a host, such as `vercel.app`, `github.io` and `blogspot.com`), written by `scripts/gen-public-suffixes.js`, which marks the rules of the private section (since rule set 0.1.9, so that `hasIcannSuffix` can tell a country or generic ending from a hosting service's domain). The list's algorithm applies: an exception rule wins, then the rule with the most labels, wildcard rules included; with no match, the last label. The list alone is not enough: a hosting service that gives each customer a host of its own but never asked to be on the list would make all its customers one organisation, so `acme.wordpress.com` would own `spam.wordpress.com`. A short hand list next to it (`TENANT_DOMAINS` in `util/public-suffix.js`) adds such services as if they were in the list's private section, each only with the service's own page that says each customer gets a host under its domain, named in the code (read on 2026-11-12): `wordpress.com`, `neocities.org` and `ghost.io`. Known gap: other services of the kind that are not on the list count as one organisation for all their customers, so a hidden link from one customer's site to another's is not reported. Their pages refused a script or did not say it for tumblr.com, substack.com, weebly.com, squarespace.com and medium.com; a review of 2026-11-12 named more that the list lacks (glitch.me, jimdosite.com, jimdofree.com, mystrikingly.com, webnode.com, godaddysites.com, hashnode.dev, beehiiv.com, canva.site, tilda.ws, wpcomstaging.com, livejournal.com, typepad.com, railway.app, 000webhostapp.com, mybigcommerce.com, mailchimpsites.com, ucoz.com, bigcartel.com, mykajabi.com), none of them checked against its service's pages. A name longer than 253 characters, which DNS does not allow, has no registered domain. Blogger's country domains (blogspot.co.uk) are no longer on the list; Blogger serves every blog on blogspot.com. The list changes every week or so; the copy and the hand list are updated by hand (CONTRIBUTING.md), and a change of either is a change of the rule set.


## A local site that names its deployed address

A project's pages name the address the site is deployed at, in canonical links and in the sitemap. Audited on `http://localhost:3000`, such a page would not be indexable (`canonical_elsewhere`), so every check whose unit is an indexable page would skip it, and `seo.canonical.cross_host` would fail on it. When a crawl of a local site is told that address (`site_url` on `crawl_start`; ARCHITECTURE.md 4.5), a canonical URL and a sitemap entry on exactly that origin are recorded as the same path on the local server. The checks themselves do not change and do not know about it: they read the record. `href` in a canonical keeps what the page sent, so `seo.canonical.relative` still judges the page's own text. Finding ids are unchanged, because they are built from the page's URL, which is the local one either way.

## Fixes and their verification

`/seekwide:fix` (ARCHITECTURE.md 4.13) plans changes for the findings of nine checks: `seo.title.missing`, `seo.title.duplicate`, `seo.title.multiple`, `seo.meta_description.missing`, `seo.meta_description.duplicate`, `seo.meta_description.multiple`, `seo.canonical.missing`, `seo.social.og_incomplete` and `seo.sitemap.missing`. A fix never changes a finding, an id or a score; only the next audit does. When that audit verifies fixes, a finding that is gone counts as closed only if its check looked at the same unit again. The unit of each of the nine checks is recorded next to the fix (`FIXABLE_CHECKS` in `repo/fixes.js`), and a test holds that table to what the checks do. Change it together with the check.

Notes:

- Duplicate checks (`seo.title.duplicate`, `seo.meta_description.duplicate`, `seo.content.duplicate_body`) return a result for every page in the unit set. Failing results give the size of the group in `evidence` and list its other pages in `related_urls`. Evidence never copies page text in bulk: lists in evidence hold at most five entries.
- `seo.title.too_long` estimates width with Arial advance widths (units per em of 2048) at 20 px. Characters without a table entry count as 1139 units; CJK and other full-width characters count as 2048. Evidence: `{observed: {characters, estimated_px}, expected: '580 px or less'}`.
- `seo.canonical.multiple`: compare normalized URLs. A header canonical and a link element that name the same URL are not a conflict.
- Headings and visible text (`word_count`, `text_hash`, `text_excerpt`) leave out the fallback of a React Suspense boundary that the page's own streaming script completes: the streamed content that replaces it is in the document too, so counting both counted a page's headings and text twice (a login page had two identical `h1`). See *Revealed by the page's own script* in the security module for how such a boundary is recognised. The fallback's links and images are kept, because a crawler that runs no script sees them.
- Duplicate checks say "1 other page uses" and "2 other pages use", with the verb in agreement.
- A check that needs `sitemap` and is skipped because sitemap files were found but none gave URLs says why: the site refused the crawler's request (with the status), or the files gave no URL that could be read.
- Selectors: `head > title`, `meta[name=description]`, `link[rel=canonical]`, `h1`, `html`, `meta[name=viewport]`. Site-level checks use no selector.
- `http_probe` is null, so `seo.https.not_enforced` has no unit, when the http request failed or was refused (429 or a bot challenge), when robots.txt does not allow it, or when the site is on a port other than the default.
- A redirect that leads to a file and not a page (judged by its URL) is followed with a `HEAD` request. When the HEAD fails or answers 400 or above (429 and bot challenges excepted), a `GET` limited to 16 KB is sent and its answer is used. The answer sets the redirect's `final_status`, so `seo.redirect.broken` and `links.internal.broken` see it, but the file gets no record of its own.

**`X-Robots-Tag` lines with Bing's AI directives** (rule set 0.2.0). Google's robots meta tag page shows a user agent before the rules (`X-Robots-Tag: otherbot: noindex, nofollow`) and says rules without a user agent are valid for all crawlers; it documents nothing about `ai-training:` or `ai-grounding:`, which Bing's blog of 2026-10-30 defines as directives (`X-Robots-Tag: Bingbot: ai-training:disallow`). A line such as `ai-training:disallow, noindex` could therefore be read by Google as rules for a user agent named `ai-training`. Seekwide reads `ai-training:` and `ai-grounding:` as directives in its Google reading too, so the `noindex` after them is not lost, and records the rules that came after such a directive in its own line (`x_robots_unclear`): a noindex finding is `likely`, with the reason in its detail, only when every `noindex` of the header is one of those and the meta tag gives none; a `noindex` on a line of its own stays `confirmed`.

### Core Web Vitals (`checks/seo/cwv.js`)

These checks read `ctx.vitals`, which `vitals/measure.js` collects from two Google services before the checks run (`docs/ARCHITECTURE.md`, 4.11). The checks themselves do no I/O.

| Id | Unit | Fails when | Sev / W | Conf | Needs | Doc |
|---|---|---|---|---|---|---|
| `seo.cwv.field_lcp` | The site's origin when the Chrome UX Report has a Largest Contentful Paint value for it (`url` = null, `selector` = `origin`), and each tested page it has a value for | the 75th percentile is above 2500 ms | medium / 3 | confirmed | field_data | LCP |
| `seo.cwv.field_inp` | The same, for Interaction to Next Paint | the 75th percentile is above 200 ms | medium / 3 | confirmed | field_data | INP |
| `seo.cwv.field_cls` | The same, for Cumulative Layout Shift | the 75th percentile is above 0.1 | medium / 3 | confirmed | field_data | CLS |
| `seo.cwv.lab_lcp` | Each tested page with a lab Largest Contentful Paint value | the value is above 2500 ms | low / 2 | likely | lab_data | LIGHTHOUSE_LCP |
| `seo.cwv.lab_cls` | Each tested page with a lab Cumulative Layout Shift value | the value is above 0.1 | low / 2 | likely | lab_data | CLS |
| `seo.cwv.lab_tbt` | Each tested page with a lab Total Blocking Time value | the value is above 200 ms | low / 1 | likely | lab_data | LIGHTHOUSE_TBT |

Notes:

- **Tested pages.** Measuring is slow and rate-limited, so only a few pages are measured: 3 by default, at most 10. The start page comes first when it is indexable. The other indexable pages are grouped by `templateSignature` (first path segment and number of segments), and one page is taken from each group, largest group first (then the group whose pages are closest to the start page, then by signature). Inside a group the page with the smallest `depth` is taken, then the first by URL; a page found only in the sitemap comes last. A slow template shows on every page that uses it, so one page per group says the most per request. When more pages are asked for than there are groups, the groups are gone through again for their next page. Each tested page records why it was chosen.
- **Field data** is what real Chrome users on phones experienced over the last 28 days, from the Chrome UX Report API (`formFactor: PHONE`). The value compared is the 75th percentile, as Google's own assessment does. Phones are used because the lab test also emulates a phone and because the documented thresholds are the mobile ones. The origin record covers every page of the site; a tested page has its own record only when it has enough visits. An origin or page the report has no data for is not a unit: that says the page has too few visits from Chrome users, nothing about its speed.
- **Lab data** is one simulated page load by PageSpeed Insights (`strategy: MOBILE`, `category: PERFORMANCE`), which runs Lighthouse on an emulated mid-range phone. Times are rounded to whole milliseconds and the layout shift score to three decimals before they are compared. A page PageSpeed Insights could not test is not a unit.
- **Interaction to Next Paint has no lab check.** A page load without a user has no interactions, so Lighthouse cannot measure it. Total Blocking Time is the lab stand-in; it is not a Core Web Vital, which is why it weighs least.
- **Confidence.** A field value is a measured fact about real visits, so the field checks are `confirmed`. A lab value comes from one simulated load and changes from run to run, so the lab checks are `likely`: a value near the threshold is worth a second run.
- **When the data is missing.** `field_data` is provided when the Chrome UX Report API answered for the origin or for a tested page, with a record or with "no data". Without a Google API key it is never provided, because that API requires one. `lab_data` is provided when PageSpeed Insights returned values for one or more tested pages. When Google refuses a request (no quota, a key it does not accept), does not answer in time, or the site is on the user's own machine (or the crawl does not record that it is not), the capability is missing and the checks that need it are skipped. The skip reason is the collector's plain statement of what happened. A missing capability never fails the audit.
- Evidence, field: `{observed: {p75_ms, rating, good_loads}, expected: 'A 75th percentile of 2500 ms or less', detail}`. For layout shift, `p75` replaces `p75_ms`. `rating` is `needs improvement` or `poor` (above 4000 ms, 500 ms and 0.25). `good_loads` is the share of page loads inside the good range, as a percentage, and is left out when Google's histogram does not use the same boundary. `detail` names the form factor, the collection period, and whether the value is for the whole site or for the page.
- Evidence, lab: `{observed: {lcp_ms | cls | tbt_ms, rating}, expected, detail}`. `rating` uses 4000 ms, 0.25 and 600 ms as the upper bounds of "needs improvement", the mobile bounds Lighthouse documents. When Google was redirected and tested another URL, `detail` names it: the finding stays on the tested page, because that is what a phone visiting it gets.
- Thresholds live in `vitals/thresholds.js`, so the checks and the reports cannot disagree.

Notes:

- "Distinct internal link target" means distinct normalized `link.url` values among links with `internal: true` and a non-null `url`. A page that links to itself is included (except for `links.internal.nofollow`).
- A report group whose findings have both confidences is shown as likely and says how many are ("Likely for 3 of 10 findings, confirmed for the rest"); `audit_run`'s top group has `confidence: likely` and `likely_findings`.
- In a report, a group of the links module says how many distinct links its findings are about and on how many pages ("66 findings (3 links on 22 pages)"), counted by the target URL the evidence names, else the selector, and shows one finding per link first; `audit_run`'s top groups carry `distinct_links` and `pages` when they are fewer than the findings. A link in a menu or footer is one fix however many pages repeat it.
- `links.internal.broken` and `links.internal.redirect` look the target up in `ctx.pageByUrl`. A target with no record (not crawled) is not a unit.
- The crawl does not fetch pages of other sites; a robots.txt that redirects to another host is the one thing it reads from there. A redirect that leaves the site has `final_external: true` and `final_status` 0; its destination is checked with the external links, and a broken one is reported by `links.outbound.broken` on the page that links to the redirecting URL.
- External link results: `broken` means 404, 410, or a host name that does not exist. A site that refuses automated requests, a robots.txt rule, a timeout or a temporary DNS failure gives `unverifiable`, which is not a unit.
- **Hosts that are never contacted** (rule set 0.1.9). A link to Google Play (the store, its image host `play-lh.googleusercontent.com`, its short links `play.app.goo.gl` and the old `market.android.com`) or to a social platform, its short links or its image hosts (`util/off-limits.js`: Facebook, Messenger, Instagram, Threads, WhatsApp, X, LinkedIn, Pinterest, TikTok, YouTube, Telegram, Discord, Snapchat, Reddit, Tumblr, VK, Bluesky; Pinterest, YouTube and Instagram under any country or generic ending of the ICANN section, `youtube.de`, but not a customer's name under a hosting service, `pinterest.github.io`) is left out of the external link check and never requested, its robots.txt included; a redirect step that leads there ends the link as `unverifiable`. Seekwide does not scrape these platforms (the user's decision of 2026-11-13). The rule holds for every request the plugin sends: `safeFetch` refuses such an address and every redirect to one, and every requester wraps the fetch it is given in the same guard (`guardFetch`), so a robots.txt that redirects there is not followed either (the review of batch 1 found that path open). Such links are not units of `links.outbound.broken`; the run counts them (`run.not_requested`) and the report names the platforms' own domains (`facebook.com`, never the host a page wrote) as not checked, by rule. A crawl never starts at such an address (`crawl_start` refuses it) and stops, as failed, when its start URL redirects there.
- `links.orphan.sitemap_only`: build the set of linked URLs from every internal link on every html page, adding `ctx.resolve(link.url)?.url` so a link to a redirect counts for its destination. A link from a page to itself does not count.
- Selectors of the form `a[href="…"]` escape `\` and `"` inside the href.
- `links.anchor.uncrawlable`: Google's page (LINKS, read 2026-11-12) asks that the URL in an `<a>` element resolve to an actual web address that its crawlers can send requests to, and names `javascript:` hrefs as not recommended; both of its examples open a page (`goTo('products')`, `window.location.href='/products'`), and it says Google cannot reliably extract URLs from elements with no href or from script events. One rule covers every case: a link fails when what it opens is not in its href as a web address. A `vbscript:` URL is a script like `javascript:`, and a `data:` URL carries its document inside the link, so neither is an address a crawler can request. A script that only prints, goes back or does nothing, on an element with no `onclick`, opens no page at all: it is a control that looks like a link (a print button, a back button, a menu toggle), there is no page for a crawler to find, and it is not a unit. With an `onclick` or another script handler, the handler does whatever the link does, as on an element with no href, so it fails. Known gap: a handler on an element around the link (a delegated click handler) is not seen, so such a script link with no destination is not a unit. `mailto:`, `tel:` and other schemes that hand the link to another program open no page, so they are not units that fail.
- `links.internal.nofollow`: Google's page (QUALIFY_LINKS, read 2026-11-12) says that links marked nofollow will generally not be followed, and that for links within your own site the robots.txt disallow rule is the way to stop a fetch. A page is withheld only when every link to it on the page is nofollow: a nofollowed copy of a link the page also has without nofollow (a mobile menu that repeats the footer) withholds nothing. Share, comment-reply, cart and export links carry a query string and are actions, not pages to index; a link to a fragment of the page itself goes nowhere new; a target robots.txt disallows already gets the treatment Google recommends. Known gap: a page with a query string that is a real page (a pagination URL `?page=2`) is not a unit.
- `links.internal.redirect`: Google's page on HTTP status codes (HTTP_STATUS, read 2026-11-12) treats 301 and 308 as a strong signal that the target should be processed and 302, 303 and 307 as a weak one, and its site-move page (SITE_MOVE, read 2026-11-12) asks to update internal links to the new URLs. A temporary redirect is often meant: a login page for an app entry, a regional edition, an add-to-cart action. So such a finding is `likely`, and a temporary redirect to a page that carries the link's own address in its query (a login that sends the visitor back) is not a unit. A chain with any permanent hop stays `confirmed`.
- `links.anchor.empty` and `links.anchor.generic`: Google's page (LINKS, read 2026-11-12) marks empty link text and generic text such as "click here" as bad and uses an image's `alt` and, for an empty link, its `title` as anchor text; it says nothing about `aria-label` or fragment links. A link marked `aria-hidden` is left out of what screen readers read, and sites use it for copies (a heading's permalink, a card's image link beside its title link); a link into the page itself leads to no other page. When another link on the page to the same address is named, Google has anchor text for that address and a visitor has a named link to it, so an unnamed or generic copy passes. Known gap: a screen reader user who reaches the unnamed copy first hears no name; that is an accessibility finding, not one about crawling.
- Generic-anchor list (compared after lower-casing and removing punctuation): English "click here", "here", "read more", "more", "learn more", "this", "link", "this link", "this page", "continue", "continue reading", "details", "more info", "more information"; Turkish "tıklayın", "buraya tıklayın", "burada", "buraya", "devamı", "devamını oku", "daha fazla", "detaylar", "incele"; German "hier", "hier klicken", "mehr", "weiterlesen", "mehr erfahren"; Spanish "aquí", "haz clic aquí", "leer más", "más", "ver más"; French "ici", "cliquez ici", "lire la suite", "en savoir plus", "plus".

## Security module (`checks/security/`)

Signs that a site was hacked or misused, measured from outside, and the security headers of its start page. Google warns about or demotes hacked sites, and a hacked site is usually built to hide the hack from its owner, so the module looks for what the owner does not see.

**What it looks at.** Only the responses the crawler fetches anyway: the same pages, with the same user agent, robots.txt and pacing. It requests no path the site does not link to or list (no `/wp-admin/`, `/.env` or `/.git/`), never tries an exploit, and never sends a second request with other headers to look for cloaking. That has a limit that every report states: many hacks show their spam only to Google's crawler or to visitors who come from Google, so a clean result does not prove a clean site. Search Console's Security issues report is where Google says what it found.

**The signals** are read while a page is extracted (`extract/security.js`, `extract/concealment.js`, `extract/terms.js`, `extract/security-headers.js`) and stored as `PageRecord.security`. A record without it (a crawl made before the module existed) is not a unit of any security check.

- *Hidden by its markup*: an element, or an element above it, that has the `hidden` attribute (not `hidden="until-found"`, and not together with an inline `display` value other than `none`), or an inline `style` with `display: none`; `visibility: hidden` or `collapse` (undone by `visibility: visible` further down); a font size of 1 px or less (undone further down by an absolute font size, or by any element with a `class`, through which a style sheet may set one; `em`, `%` and `inherit` stay 0); an offset that moves the box 1000 px or more to the left or up, off the page (a negative `left` or `top`, or a positive `right` or `bottom`, with `position: absolute`, `fixed` or `relative`; a negative `margin-left` or `margin-top`; or the x or y of a `translate` in `transform`; em and rem count as 16 px, and percentages and viewport units do not count, because an off-canvas menu moved by -100% is a menu); or a width or height of 2 px or less with `overflow: hidden` or `clip`, no padding along that axis (the `padding` shorthand read side by side, the longhands and the logical properties), and no `clip` or `clip-path`. Style sheets, classes and scripts are not read, and at most 20,000 characters of a `style` attribute are. Not counted: `opacity: 0`, which animation libraries use as the start state of content they fade in; `text-indent`, which moves the text of a box that is still there (a logo drawn as a background image); and the 1 px box with `clip`, the usual way to keep text for screen readers.
- *Built to be opened*: content a visitor can reveal, which Google allows (tabs, accordions, menus, pop-ups), as the markup shows that a control on the page opens it (since rule set 0.1.8). A *control* is a `<button>`, `<summary>`, `<input>` or `<select>`, a link with an `href`, an element with the role `button`, `menuitem`, `tab`, `combobox`, `switch` or `link`, or one with a `tabindex`. A hiding element is built to be opened when its previous element sibling is a `<summary>`, or a control that says with `aria-expanded` or `aria-haspopup` that it opens something, or an element with such a control among its first 20 element children (a button wrapped in a box); when it is a tab panel (`role="tabpanel"`) whose `aria-labelledby` names an element with the role `tab`; when it has `x-show` and sits inside an Alpine.js component (the nearest element with `x-data` around it, not itself) that carries an event binding (`@…`, `x-on:…`) outside the hiding element (Alpine.js runs `x-show` only inside a component); when it has `v-show` and the page has an event binding (`@…`, `v-on:…`) outside it; or when its `id` is named, from outside the element and by an element its own markup does not hide (`hidden`, `display: none`), by a control's `aria-controls`, `popovertarget`, `commandfor` or `aria-describedby` (a tooltip), by the `href="#id"` of a link, or, on any element, with or without `#`, by one of `data-target`, `data-bs-target`, `data-toggle-target`, `data-tab`, `data-tab-target`, `data-modal`, `data-modal-target`, `data-popup`, `data-open`, `data-reveal-id`, `data-micromodal-trigger`, `data-controls`, `data-panel` and `data-fancybox-src`, or with `#` by `data-src` (at most 20,000 `data-*` values are collected; the others always are). The ids and bindings are read from the whole page before the scan. A role (`dialog`, `menu`…) or an attribute (`popover`, `aria-modal`, `x-cloak`) alone no longer makes an element openable: before 0.1.8 one attribute did, so injected spam needed only `role="dialog"`, `popover` or a bare `<span aria-expanded>` in front of it (security review F9), and a review of 0.1.8 found that an element naming itself (`<div id="q" aria-controls="q">`), a `<p>` or `<link>` with `aria-controls`, a hidden link to `#id` and an `x-show` with its own `@click` passed too; all of these now count as hidden. A plain button or link right before an element does not make it openable: the last element of a page is often a back-to-top button, and injected content often comes right after it. A hidden element keeps every element that hides it, up to four of each kind; when four are kept, one that hides for certain takes the place of one a control opens, so wrappers built to be opened around a hidden block cannot push its own hiding out. A link counts as hidden when one of them is not built to be opened.
- *Revealed by the page's own script*: React's streaming server rendering (React 18 and later; the Next.js App Router) sends a Suspense boundary's content after the rest of the page in `<div hidden id="S:n">`, leaves `<!--$?--><template id="B:n"></template>` (the fallback) `<!--/$-->` where it belongs, and moves it there with an inline call as the page loads. A hidden element counts as built to be opened, for its own `hidden` attribute only, when all of this holds (`extract/react-stream.js`): it is a segment of the shape React writes, with no inline `style`: a `<div hidden>` or `<table hidden>` with the segment's id, or, in React's table modes, the `<table hidden>` around a `<tbody>`, `<tr>` (inside the `<tbody>` the parser adds) or `<colgroup>` with the id (since rule set 0.1.7; React's script moves only the children of the element with the id, so any other element, such as a link that is itself hidden, is never shown); an empty `<template>` with the other id of the call comes before it in the document, in a place the page renders (since 0.1.7: not in `<head>`, and not inside a `<video>`, `<audio>`, `<canvas>`, `<object>` or `<datalist>`, whose content is fallback content); and after it an inline script of a JavaScript type, not `nomodule`, has as a top-level statement (at the start of the script or after a `;` outside any bracket) a call `$RC("B:n","S:n")` or `$RR("B:n","S:n",…)` (the template's id, then the element's) or `$RS("S:n","P:n")` (the element's id, then the template's), with that function defined (`$RC=function`, or `function $RC(`) by a top-level statement of an inline script before the call. The script is read with comments removed and string literals set apart, so a definition or call in a comment, inside a string, in a block (`if (false) {…}`) or in an expression (`a && $RC(…)`) does not count. For `$RC` and `$RR` the template must also follow a `<!--$?-->` comment and the boundary must be closed by `<!--/$-->`, with nested boundaries counted. When ids repeat, the first element with the id counts, as for `getElementById`, whatever its namespace (since 0.1.7, an earlier SVG element with the id takes it, and the segment stays hidden). Every other way of hiding inside, on or above the segment still counts. The page's script moves the segment's content to its template, so the content counts as hidden when an element hides it in either place: above the template (a boundary inside a `display: none` box) or above the segment where it is served. The text of the replaced fallback still counts for spam terms and writing systems. To keep the work linear, at most 100,000 sibling nodes are looked at in all to find a document's fallbacks; a boundary past that is not read as revealed.
- *Another site*: a host that is not of the site's organisation (*Which hosts are the site*), reached by a link that is not a share link. A *share link* (`isShareLink` in `extract/share-links.js`, since rule set 0.1.8) goes to a share service's own share endpoint and carries one or more addresses, every one of them on the site (its pages, its host name, or the deployed site of a local crawl): in every value of the endpoint's parameter for the address (which must hold one address, with no space in it), and in its text parameter, where every address (written with `http://`, `https://` or `www.`) must be the site's too. Other parameters (an image in Pinterest's `media`, Facebook's `redirect_uri`, a `quote`) are not read: they do not change where the link goes, which is the share service. The endpoints, matched by exact host without `www.` and by path without letter case or a trailing slash: Facebook `/dialog/share` (`href`), `/dialog/feed` (`link`), `/sharer/sharer.php`, `/sharer.php` and `/share.php` (`u`); X and Twitter, also on mobile.twitter.com, `/intent/tweet`, `/intent/post` and `/share` (`url`, and `text`), and `/home` (`status`, as text); LinkedIn `/sharing/share-offsite`, `/shareArticle` and `/cws/share` (`url`); Pinterest `/pin/create/button` (`url`); WhatsApp `wa.me/` with no phone number (`text`) and `/send` on api.whatsapp.com and web.whatsapp.com without `phone` (`text`); Telegram `/share/url` on t.me and telegram.me (`url`, and `text`); Tumblr `/widgets/share/tool` (`canonicalUrl`) and `/share/link` (`url`); VK `/share.php` (`url`); Reddit `/submit` (`url`); Mastodon Share `/` (`url`, and `text`). The sources, read on 2026-11-12, are in the code: the share dialog and feed dialog pages of Facebook, Telegram's share widget page, WhatsApp's page on links (which says that `wa.me/<number>` opens a chat with that number), Tumblr's share button page and Mastodon Share's page; X's, Pinterest's and VK's pages refused a script, and Facebook's `sharer.php`, X's `/share` and LinkedIn's `/shareArticle` and `/cws/share` are on no page today but are what the share menus of the validation pages use; Facebook's `/share.php`, `mobile.twitter.com`, X's `/home?status=` and Tumblr's `/share/link` are older forms that share-button code still writes, added after a review of 2026-11-12. Known false positives: a share link on a country domain of Pinterest (`pinterest.co.uk`) or a country subdomain of LinkedIn (`uk.linkedin.com`), which are not on the list. Before 0.1.8 a link to any of these hosts whose query named the site was a share link, so `t.me/<channel>?ref=acme.com`, `wa.me/<number>?text=acme.com` and pages on Facebook, VK and Reddit passed (security review F1). An e-mail link is not a web address and never counts. Links to the organisation's own hosts and share links are left out of `hidden_links` and `visible_hosts`; links to the site's name under another ending are kept in both, for the check to decide. Measured on 2026-11-12 on the 205 pages of 17 sites saved by the validation, offline: the 79 share links on them are share links under both rules, and the six sister domains that the 0.1.0 rule made the site's own (wordpress.tv, wordpress.com and jobs.wordpress.net on wordpress.org; gov.wales and costofliving.campaign.gov.scot on gov.uk, whose registered name `gov` matched any `gov.<ending>`; one on yoast.com) are linked visibly or nowhere hidden, so no finding was added or removed.
- *Concealed link*: a link to another site that is hidden by its markup, or whose whole text is one punctuation character (`\p{P}` or `|`) with no `aria-label` and no `title`, which is Google's example of a link on one small character. Every other link to another host is visible, and its host is one of the page's `visible_hosts` (at most 1000). `hidden_links` holds, for each host the page links to only in concealed links, the first such link and their `count` (at most 200 hosts); its `index` is the link's position in the document's `<a>` elements, which is its position in `links` while the record has room for it. Every `<a>` is read, however many the page has: since rule set 0.1.8 a link past the 5,000 the record keeps is read from the element itself, so padding a page with links no longer pushes a hidden one out of the scan (code review A3), and so is a link whose address is longer than the 2,048 characters a URL may otherwise have (its host counts; the address is clipped). Links inside a declarative shadow root (`<template shadowrootmode>`), which a browser shows inside the element around it, are read under that element's hiding; they are not in `links`, so their `index` is -1. The scan follows at most 10,000 hosts of visible links and 10,000 of concealed ones per page, not a number of links, and a host is dropped from the concealed ones as soon as the page links to it visibly; a page that reaches a cap says so in `limits_reached` (`security.hosts`, `security.hidden_hosts`, `security.visible_hosts`, `security.embeds`, `security.references`), and the audit's notes name such pages. SVG `<a>` and `<area>` links are not read: Google follows only `<a href>` elements.
- *Embed*: a `<script src>` (of a JavaScript type) or an `<iframe src>` on another host. A frame is *hidden* when its width or height is 2 px or less (the inline style wins over the `width` and `height` attributes), or when its markup hides it as above. A media or map player (a path segment `embed` or `player`, or a host that starts with `player.`) hidden only by an element around it is waiting to be opened (a video lightbox) and is not hidden; one whose own markup hides it is.
- *Spam terms*: matches, as whole words in lower-cased text, of the lists below in the whole visible text (text hidden by CSS is part of it, the headline too) and the words of external link URLs. Titles and meta descriptions are not counted, because they repeat the headline. *Topic words*: the spam terms and the topic words of a category in the titles, meta descriptions and headings.
- *Writing systems*: letters per system in the first 50,000 characters of the visible text: Latin, Cyrillic, Greek, Arabic, Hebrew, Devanagari, Thai, Hangul, Chinese and Japanese characters (one system), and `other` for every other letter. The *site's systems* are those with 5% or more of the start page's letters, known when the start page has 200 letters or more. A page's *foreign system* is the largest system that is not Latin, not `other` and not one of the site's, with at least 100 of the page's letters and 30% of them.
- *Security headers*: read from the full response headers the way browsers read them (below).

Site-level checks use the *start page* (`ctx.resolve(crawl.start_url)`) when it is an html page with the signals; without one they have no unit. Text from a page that goes into evidence is clipped.

Notes:

- **Why a hidden link counts only when its site is not linked visibly, and not when it is built to be opened.** Google's spam policies name text positioned off-screen, a font size or opacity of 0 and a link on one small character, and say that accordions, tabs, sliders, tooltips and text for screen readers are not a violation. Google describes content injection in hacked sites as hidden links or hidden text added through CSS or HTML. Such links are most often hidden with `display: none` or an off-screen box, while menus, tabs and pop-ups hide links with the same markup. So an element built to be opened does not hide, and a concealed link counts only when no visible link on the crawled pages goes to the same site (a menu hidden on one screen size links visibly somewhere else). Opacity is the one technique Google names that is not read, because animated pages start most of their content at opacity 0. White text on a white background and text behind an image need rendering and are not measured. Known gaps: an offset of less than 1000 px, spam inside `<noscript>` (text, for a parser that runs scripts), a hiding element whose `id` happens to be named by an unrelated control (a skip link to `#footer`), hiding through a style sheet, and markup written against the rule: whoever writes the page can also write the control that names the hidden element (`<a href="#x">` before `<div id="x" style="display:none">`), and no rule read from the markup can tell such a control from a real one. Known false positives that remain: a dropdown that a plain button or link opens without `aria-expanded` (Bootstrap's `data-toggle="dropdown"` link without it, jQuery UI accordions whose marks a script adds), a control separated from its panel by another element, a dialog or popover that a script opens with no control that names it (a cookie notice, a newsletter pop-up, a button with only an `onclick`), a Stimulus target hidden with `hidden`, each holding links to other organisations' sites that are linked nowhere visibly, and slides of a slider that are not marked as tab panels; on the 205 validation pages the stricter rule of 0.1.8 changed no finding: every hidden block with links to other sites that the 0.1.7 rule exempted followed a real `<button>` with `aria-expanded` or `aria-haspopup` (nextjs.org, wordpress.org, webtekno.com), except one wordpress.org `role="dialog"` modal whose links go to sites the page links to visibly; `likely` and the evidence's hiding element are there for them. When such a block carries spam terms, `security.content.spam_terms` reports the page as well, because it counts hidden text and link addresses.

- **Writing systems.** Google's guides to the Japanese keyword hack and the gibberish hack describe spam pages in another language, often in folders the site does not link to; such pages are found only when a link or the sitemap leads to them. Languages are mapped to systems by their primary subtag (`ja`, `zh`, `yue` → Chinese and Japanese characters; `ko` → Hangul; `ru`, `uk`, `bg` and the other Cyrillic languages; `el`; `ar`, `fa`, `ur` and the other Arabic-script languages; `he`, `yi`; `hi`, `mr`, `ne`; `th`; `sr`, `kk`, `uz` in either of their two systems), or by a script subtag (`sr-Latn`, `zh-Hant`) when there is one; any other language is Latin. Latin script is never a foreign system: product names, code and English pages on a site in another script are common, and spam in Latin script is what `security.content.spam_terms` looks for. Shares are counted in letters, and one Chinese or Japanese character carries about as much as a short English word, so a spam page in Japanese inside the site's English template can have fewer than half of its letters in Japanese; hence 30% and not a majority.
- **Two results: a score and a count.** The header checks count toward a result of their own, `security_headers` (`score_group` on the check, `SCORE_GROUPS` in `config.js`), and the module's `security` score covers the five checks for signs of a hack. A clean site with three headers missing scored 79 to 83 when the two were one number, which a reader takes for a security problem with the site; the headers protect visitors and say nothing about a hack. Since rule set 0.1.7 the headers are given as a count, not a score (`COUNTED_SCORES` in `config.js`): `count` is how many of the scored header checks that looked at the start page passed, out of how many did (`{passed: 0, of: 3}`, or 2 on an http site, where Strict-Transport-Security does not apply), `score` is null, and `note` says it in words ("0 of 3 recommended headers set. A count, not a score."). As a score, a site without the three headers got "Security headers 0/100" (example.com did), which reads as a verdict on the site; the count says what was measured, and it is as deterministic. `audit_run`, both report formats, the run index (`counts`), the comparison of two runs (`from_count`, `to_count`, and `delta` as the change in the count) and the skills give the count. A run stored before 0.1.7 keeps its score and is shown with it. A report shows the two as two lines ("Security" and "Security headers"), and the findings of both stay in the `security` module. Without the deployed site (a local crawl) the headers have no count (`count: null`), with the reason in `note`, and the security score keeps full coverage.
- **React streaming.** On nextjs.org the whole footer arrives as a streamed boundary, so its links to other sites were "hidden by the hidden attribute" on 22 of 25 pages, with a security score of 75. The page's own script reveals them as it loads, so they are not hidden from visitors. The exemption needs every part of the pattern React writes, in document order, and excuses only the segment's own `hidden` attribute. Known gap: a page that forges all of it with a script that does nothing (defines `$RC` as an empty function, as a top-level statement) keeps such a block hidden from visitors and from this check; that takes markup written against this rule, not the hiding that injected spam uses (`display: none`, an off-screen box), which still counts inside and around a boundary and where its content is moved. A review of 2026-11-12 found that the first version also accepted the pattern in comments, strings and dead code, and judged a segment only where it is served; both are closed. Three ways to close the gap were measured on 2026-11-12 against the 19 nextjs.org and vercel.com pages saved by the validation, the excerpts kept from them, and forged pages, and none was kept: requiring React's own runtime (its exact code, or a body that looks elements up by id) stops an empty `$RC`, but a page that copies React's runtime and adds one statement that makes it inert (a `throw` before the call, a no-op `requestAnimationFrame` or `$RB.push`) still passes, and an exact match would lose the exemption, and bring the false alarms back, with every React release that changes the runtime's code; requiring other React or Next.js markers (`<!--$-->`, `self.__next_f`) stops nothing a forger cannot add in one line, and the Next.js markers would fail React streaming on other frameworks; reporting, as a weaker finding, every link of a revealed block to a site no visible link goes to reports the footers of nextjs.org and vercel.com, the false alarm the exemption exists for. What remains: the spam-term check reads such a block like any other part of the page, so it reports there what it would report anywhere else (two or more listed terms of a category the start page is not about), with the same limits: a single term, terms off its lists, a term written with an invisible character or a look-alike letter, a term only in an `alt` or `title`, and two link texts that touch without a space ("viagra" and "cialis" read as "viagracialis") are not counted. A review of 2026-11-12 also found four ways a block could take the exemption without the forgery, all closed in 0.1.7: a segment that is itself a link (React's script removes it), a template in `<head>` or in a video's fallback content, and an earlier SVG element that takes the segment's id; and one false alarm, React's table modes (`<table hidden><tbody id="S:0">`), now read as React writes them.
- **One hidden link.** A finding with one hidden link says that it can be the site's own (a partner's logo in a block no longer shown) and asks whether someone on the owner's side added it; the recommendation names that case before the hack. The finding, its severity and its weight do not change.
- **Embeds.** Google's guide to sites hacked with malware describes injected `<iframe>` elements, often sized to zero and hidden with CSS, and `<script>` elements that load from the attacker's domain. A tracking tag that uses a 1×1 frame outside `<noscript>` is a legitimate exception, hence `likely`. A frame inside a responsive wrapper (`height: 0` with a padding that gives the box its height) is visible. Content inside `<noscript>` is text for the parser (scripting is on), so the frames of tag managers there are not seen. Rarity has no official threshold, so `security.embeds.rare_host` is `info`; on a crawl of 25 pages every video, map or form embedded on one page is used by one page (all 14 such findings of the validation of 2026-11-12 were), so it needs 50 pages.
- **Headers are not Google ranking factors.** Google's page experience documentation lists HTTPS but no security header, and Google stated in its Search Central office hours of June 2023 that the HSTS header does not affect Search. The header checks protect visitors, which is why they are `low` or `info`. They need `live_site`: a crawl of a server on this machine (`options.local: true`) says nothing about the headers of the deployed site, so they are skipped there with that reason.
- **How headers are read.** Strict-Transport-Security: only the first header counts; it is invalid (ignored) when a directive appears twice, when `max-age` is missing or not a number, or when a directive breaks the grammar; unknown directives are ignored (RFC 6797, 6.1 and 8.1). X-Content-Type-Options: the first comma-separated value must be `nosniff` (Fetch). Clickjacking: an enforced Content-Security-Policy header with `frame-ancestors` overrides X-Frame-Options, a source list allows a framer that matches any one source, and a framer must pass every enforced policy; `frame-ancestors` in a `<meta>` policy is ignored, and so is X-Frame-Options in a `<meta>`; one X-Frame-Options value other than `deny` or `sameorigin` counts as absent, and several values that include `deny`, `sameorigin` or `allowall` block framing (HTML, 7.7; CSP 3, 6.4.2). Content-Security-Policy-Report-Only enforces nothing. Referrer policy: the last valid `<meta name="referrer">` anywhere in the document (legacy values `never`, `default`, `always` and `origin-when-crossorigin` mapped as HTML does; an invalid one changes nothing), else the last valid token of the Referrer-Policy header; with neither, browsers use `strict-origin-when-cross-origin`, which sends other sites the origin only, so a missing policy passes.
- **Not checked, and why.** Cloaking and sneaky redirects: finding them needs a request that pretends to be Google or comes from a Google search, which this crawler never sends. Outdated or vulnerable WordPress core, plugins and themes: the plugin version in a `?ver=` parameter is often WordPress's own version, the WordPress.org version APIs publish no terms of use, and the vulnerability databases that allow use by agencies need a key of each user's own; this is left for a later version. Admin accounts, file integrity and backups cannot be seen from outside; the report lists them as things to check by hand.

## Media module (`checks/media/`)

Images and video: text alternatives, the space an image takes before it loads, lazy loading, the image files themselves, captions, and video structured data. Rule set 0.1.6; the own-site rule changed in 0.1.7. Audit only: no fix exists for these findings yet.

**What it reads.** Most checks read what extraction records about `<img>`, `<video>`, embedded video players and JSON-LD (`extract/media.js`, `extract/media-image.js`, `extract/jsonld.js`). A record made before the module existed has no `videos` list (`hasMedia`) and is not a unit of any media check, because it lacks the fields the exceptions below need. The `image_files` checks also read `ctx.imageFiles`, which the audit collects before the checks run (below).

Terms:

- *rendered image*: an `<img>` on an html page that is not hidden by its own markup (the `hidden` attribute, other than `hidden="until-found"`, or `display: none` in its inline `style`) and is not a tracking pixel or a spacer (a `width` or `height` of 1 pixel or less, as an attribute or as an inline `style` in `px` or a unitless 0). Images inside `<noscript>` are text for the parser and are never recorded (ARCHITECTURE.md 4.6).
- *content image*: a rendered image that is not in the page's frame: not inside `<nav>` or `<aside>`, not inside a `<header>` or `<footer>` that is outside every `<article>`, `<main>`, `<section>`, `<aside>` and `<nav>` (the page's own header and footer, as ARIA maps them to `banner` and `contentinfo`), and not inside an element with the role `banner`, `navigation`, `contentinfo` or `complementary`. Logos, icons and badges live in the frame.
- *exposed image*: a rendered image that is not marked `aria-hidden="true"` (it or an element around it) and has no `role` of `presentation` or `none`. ARIA in HTML allows those two roles on an `<img>` without `alt`; they say the author removed the image from what assistive technology reads, as `alt=""` does.
- *spoken video*: a `<video>` on an html page that is not hidden by its own markup, not `aria-hidden`, not `muted`, and not `autoplay` without `controls`. A muted or autoplaying video without controls plays without sound in browsers (autoplay with sound is blocked), which is how background and decorative videos are made.
- *checked image file*: an entry of `ctx.imageFiles` (below). Its finding's `url` is the first html page, by sorted URL, that shows the file in a rendered image, `selector` is `img[src="<raw src>"]` of that element, and `related_urls` are the other pages.
- *own site*: a host of the audited site's organisation (*Which hosts are the site*): its registered domain (acme.com, cdn.acme.com and shop.acme.com; under a shared hosting domain such as vercel.app, only the customer's own host and its subdomains), and the same name under another ending only when a page links there visibly.

**Which image files are checked** (`checks/media/select.js`, `net/image-check.js`). Each check of a file costs requests, so at most `LIMITS.maxImageChecks` (50) distinct image URLs are checked per audit, chosen without randomness: the html pages in crawl order are gone through in rounds, each round taking the next not yet chosen `http(s)` URL of a rendered image from each page in document order, so the first image of every page comes before the second image of any. For a crawl of a site on this machine only images on the site's own origin are chosen. Nothing is requested from a site that stopped the crawl with a bot challenge or rate limiting, and when the site refused some of the crawl's page requests that way, no image on a host of its organisation is chosen: its apex, `www`, subdomains and other ports, and any host under its name with another ending, linked or not, since that may be the same organisation's server (*Which hosts are the site*; before rule set 0.1.8 only the exact host was left out, security review F6); the notes and the report say so. The files are checked after the external link check of the `links` module has finished, never at the same time, so a host that serves both sees one request at a time. For each chosen URL, in order:

1. The robots.txt of its origin is read once per audit, with the rules of 4.2. Googlebot's and Googlebot-Image's access is evaluated from it without any request for the image. When it disallows the file for the crawler (`seekwide`), or could not be read, the file is not requested (outcome `disallowed` or `unverifiable`).
2. A `HEAD` request with `Accept: image/avif,image/webp,image/*;q=0.8,*/*;q=0.5`, so that a server that chooses the format by the `Accept` header (as image CDNs do, web.dev IMAGE_CDN) shows the best one it has. The user agent is the crawler's own, as for every request.
3. When the `HEAD` fails or answers 400 or above, or answers 2xx without a usable size, one `GET` with `Range: bytes=0-0` that reads at most 1 KiB; the size is the total of `Content-Range` (206) or `Content-Length` (200). No image is ever downloaded whole.
4. Redirects are followed by hand, at most 5, and each step is treated like a first request (its origin's robots.txt is read and obeyed). In a local audit a step to another origin is not requested.

Requests to one host are sequential, `1000 / rate_per_sec` of the crawl apart, and at least the crawl-delay of that host's robots.txt (capped at `LIMITS.crawlDelayMaxSec`); up to 4 hosts are checked at once. No new request starts after `LIMITS.imageCheckDeadlineMs` (90 s); the files not reached by then are `not_checked`. Outcomes: `ok` (the final answer is below 400), `broken` (404, 410 or `dns_error`), `unverifiable` (any other status or error, a robots.txt that could not be read, a refused step, too many redirects), `disallowed` and `not_checked`. Only `ok` and `broken` are units of the file checks, except `media.image.robots_blocked`, which needs only robots.txt. An image on Google Play or a social platform is never chosen or requested (as for external links, rule set 0.1.9); the run counts such images in `run.not_requested`. The audit records the files it chose (`run.image_files`: how many distinct images the pages show, how many were chosen, the count per outcome) and says in its notes and the report's scope how many of the chosen files answered.

Notes:

- **Text alternatives.** WCAG's failure F65 applies only when an image has none of `alt`, `aria-labelledby`, `aria-label` and `title`; the HTML standard also lets an image whose content the author cannot describe omit `alt` when it is the only content of a figure with a caption. `alt=""` is the documented markup for a decorative image (HTML, WAI's decorative images tutorial, MDN), so an empty `alt` is a choice and never fails. Google calls alt text the most important image metadata and shows an image without it as its first bad example (GOOGLE_IMAGES). A tracking pixel is not content; HTML asks for `alt=""` on such images, which the check does not require. A page built by a script framework can carry its templates in the HTML (`<img :src="item.image" :alt="item.title">`); the binding sets `alt` when the page renders, so it counts as a text alternative (the validation of 2026-11-12 found all 10 false findings of the first version there). A linked thumbnail with a caption (`<figure><a><img></a><figcaption>`, as wikis and galleries write it) counts as the figure's only content, a reading slightly wider than the HTML standard's bare case. Hiding counts only on the image itself: an image inside a hidden menu, tab, slide or dialog is shown when that opens and needs its `alt` then. Known gap: an `alt` that is present but says nothing useful in other ways (a keyword list, the page title on every image) needs judgment and is not measured.
- **File names and placeholders.** F30 lists `spacer`, `image`, `picture`, `picture 1`, `0001`, `Oct.jpg`, `Chart.jpg` and `sales\oct\top3.jpg` as text that is not an alternative; HTML asks generators not to use the file name as `alt`, and MDN's example of what not to write is `alt="image"`. The other placeholder words are of the same kind. A file name is compared only when it looks machine-made (a digit, `-` or `_`, no space), and as written, so `alt="Team"` on `team.jpg` and `alt="Coca-Cola"` on `coca-cola.svg` pass while `alt="IMG_0423"` on `IMG_0423.jpg` fails.
- **Dimensions.** web.dev (OPTIMIZE_CLS) asks for `width` and `height` on images so the browser reserves the space before the file arrives, and names CSS `aspect-ratio` as the alternative; Lighthouse does not warn when `aspect-ratio` is set. An image placed `absolute` or `fixed` by its inline style moves nothing around it. A style sheet can give an image, or the box around it, a fixed size, which the crawler does not read: in the validation of 2026-11-12 the first version (all rendered images, `low`) was right on 19 of 107 pages and wrong on 11 (utility classes such as `aspect-3/1`), and most of the rest were logos, icons and card thumbnails whose box the theme fixes. Leaving out the page's frame and reading utility classes removed every wrong one but one, and 19 of 55 stayed clearly worth a change; so the check is `info` and does not change the score.
- **Lazy loading.** web.dev says never to lazy-load the Largest Contentful Paint image and calls `fetchpriority="high"` together with `loading="lazy"` unnecessary. Which image is the largest one shown first needs layout: web.dev's own heuristic (the first featured image or first content image) is stated as unaware of the viewport. So the check does not guess; it finds the page contradicting itself, an image it marks as the most important (priority hint or preload) that it also tells the browser to load late.
- **Formats.** Google Search indexes BMP, GIF, JPEG, PNG, WebP, SVG and AVIF (GOOGLE_IMAGES), so no format keeps an image out of Search; the format check is about weight. Lighthouse's modern-format audit (LH_MODERN_FORMATS) covers JPEG, PNG and BMP and leaves out images whose saving would be under 8 KiB; web.dev puts WebP's saving at 25–35 %, so a file of 32 KiB or more is where 25 % reaches 8 KiB. GIF (animation), SVG (vector) and ICO are not units. A server can choose the format by the user agent instead of `Accept`, and the crawler never claims to be a browser, so such a server shows it a legacy format that browsers do not get; that and PNG kept for exact pixels are why it is `likely`. A server that says in `Vary` that its answer depends on `Accept` or `User-Agent` chooses the format per client: in the validation of 2026-11-12 an image CDN that said `Vary: Accept` answered JPEG even to `Accept: image/webp`, so browsers very likely get another format, and such files are not units. Evidence: `{observed: {content_type, bytes, vary}, expected, detail}`.
- **Size.** No official page gives a size limit for one image. Lighthouse flags pages whose requests add up to more than 5,000 KiB and suggests aiming under 1,600 KiB in all (LH_TOTAL_BYTES); 500 KiB, about a third of that for one file, is this plugin's rule of thumb, hence `info`. A file used only with `srcset` or `<picture>` sources is not a unit, because browsers load a candidate chosen for the screen, not necessarily this file. Known gap: an image much larger than the box it is shown in needs layout.
- **robots.txt and images.** Google's page on keeping images out of search (PREVENT_IMAGES) says the robots.txt of the host that serves the image decides, that a `Googlebot-Image` rule keeps images out of Google Images and a `Googlebot` rule keeps them out of every Google search. Googlebot-Image answers to the tokens `Googlebot-Image` and `Googlebot` (CRAWLERS: one matching token is enough), and Google's robots.txt rules apply only the most specific group that matches (ROBOTS_SPEC), which gives the fallback in the table. A site can keep its images out of Google Images on purpose, hence `likely`; the evidence names the crawler and the host whose robots.txt says so. Only the own site counts, because another organisation's robots.txt is not the owner's to change, and only images shown in a page's content, because logos, icons and badges in the frame are not what people look for in Google Images: in the validation of 2026-11-12 all 10 findings of the first version were a map host and a menu-photo host of other organisations that keep everything out, and a footer badge in a folder Wikipedia keeps out on purpose. A `User-agent` line whose group has no rule at all gives that crawler no restriction; consecutive `User-agent` lines, with blank lines or other records such as `Sitemap:` between them or not, are one group (RFC 9309 2.2.4).
- **Broken images.** A 404 or 410 image is shown to visitors as a broken image and is not indexed (HTTP_STATUS). A refusal (401, 403, 429), a server error or a timeout is `unverifiable`, as for external links: many image hosts refuse requests without a browser's referrer.
- **Captions.** WCAG 1.2.2 asks for captions on prerecorded audio in synchronized media, and its technique H95 tests that each video has a `<track kind="captions">`. A `subtitles` track carries dialogue only (H95, MDN; `kind` defaults to `subtitles`), so it does not pass. Captions burned into the picture (open captions) and captions that a player script loads (a streaming format's text tracks) are also sufficient (G93, G87) and cannot be seen in the HTML, and whether a video has speech at all cannot be told from the page: in the validation of 2026-11-12, 3 of the 4 videos reported were very likely silent (a demo clip, an animation, a silent film). So the check is `info`. Google's video documentation says nothing about captions; this check is about accessibility. A video loaded by a script is not seen at all.
- **Video structured data.** Google requires `name`, `thumbnailUrl` and `uploadDate` and says that without them it may be unable to extract any information about the video (VIDEO_STRUCTURED_DATA). `thumbnailUrl` counts when it is a non-empty string, an array with one, or an object with a `url` or `contentUrl`; `name` and `uploadDate` when they are non-empty strings. A `VideoObject` in microdata or RDFa is recorded (`video_markup`) but its properties are not checked.
- **No check for a video without structured data.** Google recommends video structured data and does not require it, and says that a video that only supplements a page (a blog post, a product page) does not make it a watch page, which is where video results come from (VIDEO_BEST_PRACTICES). Which page is a watch page cannot be told from its markup: the first version listed every indexable page with a video or a player of a known platform and no `VideoObject`, and all 15 findings of the validation of 2026-11-12 were pages where the video only supplements the content. The check was removed; extraction still records the players (`video_embeds`).
- **Not checked, and why.** An image sitemap is optional (IMAGE_SITEMAPS). File names that say nothing (`IMG00023.JPG`) are discouraged by Google but are not a failure of the page. Images in CSS backgrounds are not indexed by Google and are not read by the crawler. Images and videos that a script adds, and alt text quality beyond the patterns above, need rendering or judgment.

## Smo module: social sharing previews (`checks/smo/`)

What a page gives social platforms and messaging apps for the preview of a shared link. Rule set 0.1.9; every source was read on 2026-11-13. The module never sends a request to a social platform and never pretends to be a platform's crawler, so the checks judge what the site sends against what the platforms document, not what a platform finally shows after its own cache.

**What it reads.** The Open Graph and Twitter card tags of each page (`og`, `twitter`; `og:image:url` and `og:image:secure_url` give `og.image` when no earlier property did), and `PageRecord.social` (`extract/social.js`): the placed tags (`og:title`, `og:description`, `og:url`, `og:image`) given with content only outside `<head>`, whether a Next.js App Router page streamed them into the body (the canonical rule: inline `self.__next_f` data scripts and a `<title>` in the body), where the parsed `<head>` ends in bytes of the response (`head_end`; the characters parse5 records are turned into bytes of the response's own encoding, a byte order mark included; without a place for the head, the end of the last `og:` tag), and the `rel="me"` URLs of `<a>` and `<link>` elements. JSON-LD gives each Organization, business or Person at the top level of a block or in its `@graph` with its `sameAs` count (`profiles`); one nested inside another object (an article's author, a site's publisher) describes someone else and is not read. A record made before rule set 0.1.9 has no `social` and is not a unit of the checks that need it.

Terms:

- *sharing image* of a page: its `og:image`, else its `twitter:image`, resolved against the page URL.
- *checked sharing image*: an entry of `ctx.socialImages` (below). Its finding's `url` is the first html page, by sorted URL, that gives it; `selector` is `meta[property="og:image"]` (or `twitter:image`); `related_urls` are the other pages.
- *known size* of a checked sharing image: the width and height its first bytes declare (PNG, GIF, WebP, JPEG; `util/image-size.js`), else `og:image:width` and `og:image:height` of the first page that gives it, when both are whole numbers of 1 or more.

**Which sharing images are checked** (`checks/smo/select.js`, `net/image-check.js` with `readBytes`). The images are checked after the image files of the media module, as the media module checks its files: the robots.txt of each origin first (shared with the crawl and the other checks for ten minutes; a disallowed file is never requested), at most 5 redirects, each step after its own robots.txt, one request per host at the crawl's rate (slower when robots.txt asks), through the host gates shared by the whole process, nothing new after 90 seconds. Instead of the `HEAD` and the 1 KiB `GET`, each step gets one `GET` with `Range: bytes=0-65535` that reads at most 64 KiB, the user's decision of 2026-11-13: a JPEG's frame header comes after its application segments (EXIF), which a smaller read can miss. The pixel size is read from those bytes (`size`); a format without it there (SVG, AVIF) has none, and then the page's declared size is used. In a local audit only images on the local origin are chosen, so every image the run counts as checked was requested. The run records `social_images` (images, chosen, the count per outcome, how many sizes were read).

Notes:

- **The four required properties.** ogp.me (OPEN_GRAPH): "The four required properties for every page are" `og:title`, `og:type`, `og:image` and `og:url`. WhatsApp (WHATSAPP_PREVIEWS) requires `og:title`, `og:description` and `og:url` inside the head and not empty, and LinkedIn (LINKEDIN_SHARE) lists `og:title`, `og:image`, `og:description` and `og:url` as the tags that must exist. `og:image` has its own check because without it the preview has no picture, which is what people notice; `seo.social.og_incomplete` (`info`, the one `/seekwide:fix` repairs) stays in the seo module unchanged (the user's decision of 2026-11-13).
- **Outside the head, and streaming.** WhatsApp says the tags "must be inside the <head> tag". A Next.js App Router page can send its metadata in the body, which browsers and crawlers that run scripts read; whether WhatsApp's crawler does is not documented, so the check is `likely` and the evidence names a streamed page.
- **300 KB and 1 MB.** A page that gives no Open Graph tag is not a unit: where its head ends changes no preview (the validation of 2026-11-13 judged 3 of 6 findings of the first version debatable for that reason). WhatsApp: the head "must appear within the first 300KB of the HTML". Meta (META_CRAWLERS): Open Graph properties "need to be listed before the first 1 MB". Both are read as binary units (KiB, MiB), the larger reading, so that a page between the two readings is not failed. The body is read up to `LIMITS.maxBodyBytes` (5 MiB); a head that ends beyond what was read has no place and the end of the last `og:` tag is used.
- **Absolute image URL.** WhatsApp: "The <og:image> mark-up is an absolute URL". LinkedIn's own example writes `og:image` as `//media.example.com/…`, so a protocol-relative URL passes.
- **og:url.** WhatsApp: "The <og:url> mark-up represents the canonical URL of the page. The URL should be undecorated, without session variables, user identifying parameters and counters." The parameters are read from the address as written, because `normalizeUrl` drops campaign parameters. A site can share a page under another address on purpose (a hub page), hence `likely`. Known gap: a parameter that identifies a user under another name is not recognised.
- **Preview crawlers and robots.txt.** Meta's page (META_CRAWLERS) says how to block FacebookExternalHit with a robots.txt rule and that it "might bypass robots.txt when performing security or integrity checks"; so the crawler that builds the previews of Facebook, Instagram and Messenger reads robots.txt. The crawl records, for the start page's final URL, whether the robots.txt of the site's origin lets each crawler of `PREVIEW_CRAWLERS` fetch it (`allowsAgents`, the most specific group, else `*`); a missing robots.txt allows everything, and a robots.txt that could not be read records nothing. LinkedInBot's and Twitterbot's robots.txt behaviour is not documented on a page that could be read, and Slack says it does not honor robots.txt (research of 2026-11-13), so none of them is a unit.
- **Image limits.** Facebook (FB_IMAGES): "The minimum allowed image dimension is 200 x 200 pixels", "The size of the image file must not exceed 8 MB", images under 600 × 315 display "much smaller", 1.91:1 recommended, and `og:image:width` and `og:image:height` let the crawler "render the image immediately". WhatsApp: "under 600KB", "300px or more in width with 4:1 width/height or less aspect ratio". LinkedIn: "Max file size: 5 MB", "Images less than 401 pixels wide display as a thumbnail image", 1.91:1 recommended; its minimum of 1200 × 627 for the sharing module is not a failure here, because Facebook and WhatsApp accept smaller images and LinkedIn shows them as thumbnails. A square or small image can be chosen on purpose (a logo), so the shape check is `info`; the 15 % tolerance around 1.91:1 is this plugin's rule of thumb.
- **Text alternative.** ogp.me: "If the page specifies an og:image it should specify og:image:alt." A should, not a must, hence `info`. `twitter:image:alt` counts as well.
- **X cards.** X's card pages (developer.x.com/en/docs/x-for-websites/cards/…) redirect to docs.x.com/overview on 2026-11-13, which has no card documentation. The card types come from X's own markup reference as the Internet Archive kept it on 2025-05-30 (X_CARDS); that is why the check is `info` and compares the value as written.
- **sameAs.** Google (GOOGLE_ORG) describes `sameAs` as "The URL of a page on another website with additional information about your organization", for example "a URL to your organization's profile page on a social media or review site"; Google requires no property of this markup, hence `info`. A profile entity is an Organization (or a type whose name ends in "Organization"), a type whose name ends in "Business", Corporation, NGO, OnlineStore, Store, Restaurant, Airline, Consortium or Person.
- **rel="me".** Mastodon (MASTODON_VERIFY) verifies a link in a profile when the linked page has "at least one a or link tag with a rel="me" attribute" whose href "must be equal to the URL for your Mastodon profile". Whether the profile lists the site cannot be seen from the site, hence `info`.
- **Not checked, and why.** Pinterest's `nopin` and `fediverse:creator` are preferences, not errors. Telegram's and Discord's preview rules could not be read on an official page. LinkedIn's minimum of 1200 × 627 is not applied (above). What a platform shows after its cache, and preview cards a script adds, need the platform itself.

## Aso module: the site's side of its apps (`checks/aso/`)

Apple's Smart App Banner on the pages, and the association files that let an iOS or Android app open the site's links. Rule set 0.1.9; every source was read on 2026-11-13. Store pages (App Store, Google Play) are not read in this version, and no request ever goes to Google Play.

**What it reads.** `PageRecord.social.app_banners`: every `<meta name="apple-itunes-app">` (at most 5 per page) with its `content`, whether it is in `<head>` and its line. `ctx.appFiles` (below): what the site answered at `/.well-known/apple-app-site-association` and `/.well-known/assetlinks.json`. `ctx.apps`: the apps the project profile declares (`profile.apps`): iOS app identifiers (`<Team ID>.<bundle ID>`) with whether the app opens the site's links (`universal_links`), and Android package names with whether the app is verified to open them (`app_links`). The apps are used only when the profile's `site_url` is the audited site's own host (with or without `www.`, on the same port; `util/profile-site.js`, the rule the ai module's policy follows): a profile speaks for its own host, since every host serves its own association files, so an audit of another address from the same folder (a competitor, a client) is never judged by the user's own apps, and the run notes say why the apps were not used and that setting `site_url` with `/seekwide:setup` enables the checks. Without a profile, with one that cannot be read, or with one for another site (the notes say which), it is empty.

**How the files are read** (`net/app-files.js`). For a crawl of a site that is not on this machine (`options.local` is `false`) and that refused none of the crawl's requests, `audit_run` with the aso module and `check_app_files` (default true) reads both files at the site's origin, one after the other: the robots.txt of the origin first (a file it disallows is `disallowed` and never requested; one of an origin whose robots.txt cannot be read is `unverifiable`), then one `GET` each that says it accepts `application/json`, with no redirect followed by `safeFetch` and at most `LIMITS.appFileMaxBytes` (1 MiB) read. A redirect is recorded as the file's `location` and followed by hand, at most 3 steps, each only where the crawl itself would go (*internal*: the site's host with or without `www.`, on the same port; another port, a subdomain and a sister domain are other sites) and after its robots.txt, never to Google Play or a social platform, to learn whether the file is behind it. The outcome is `answered` for a 200 whose body is neither empty nor an HTML page (a body that starts with `<`; the media type does not decide, since in the validation of 2026-11-13 one site sent its real association file as `text/html`), `not_found` for 404, 410, an empty body or an HTML page (a site that answers every unknown address with its home page or a "not found" page in HTML has no file), and `unverifiable` for anything else: 401, 403, 429 and other statuses, server errors, network errors, a body over the limit, a redirect off the site or past 3 steps. Requests to the host are spaced like the crawl's and pass the process-wide host gates. The run records each file's outcome and status (`run.app_files`), never its body.

Notes:

- **Smart App Banner.** Apple (APPLE_SMART_BANNER): "include the following meta tag in the [head] element of each page where you'd like the banner to appear", with `app-id` marked Required, "Your app's unique identifier", the number in the app's App Store link or its Apple ID in App Store Connect. A template placeholder (`app-id=myAppStoreID`) is the common failure. Whether Safari reads a tag that a Next.js page streamed into the body is not documented, hence `likely` for the head rule.
- **apple-app-site-association.** Apple (APPLE_AASA): the file is named `apple-app-site-association` "(without an extension)", placed at `https://<fully qualified domain>/.well-known/apple-app-site-association`; "You must host the file using https:// with a valid certificate and with no redirects"; universal links list app identifiers in `applinks`, App Clips in `appclips`, shared credentials in `webcredentials`; identifiers have the form `<Application Identifier Prefix>.<Bundle Identifier>`; every subdomain serves its own file. Apple's page states no content type and no size limit, so neither is checked. Since iOS 14 and macOS 11 Apple's devices fetch the file through Apple's content delivery network, which can get another answer than this crawler (a region, a firewall); a refusal is therefore `unverifiable`, never a failure. Whether Apple's network obeys robots.txt is not documented; Seekwide does.
- **assetlinks.json.** Android (ANDROID_ASSETLINKS, updated 2026-10-28): "The assetlinks.json file is served with content-type application/json", "must be accessible over an HTTPS connection", "must be accessible without any redirects (no 301 or 302 redirects)", and must be published on each host the app's links use; the examples give the statement structure above.
- **Why a missing file needs the profile.** An app that does not open the site's links needs no file, and many sites have no app. A missing file is a failure only when the profile says the app uses universal links or App Links. A file that exists is judged either way, since the site serves it to be read.
- **Only the audited host.** The file of the start origin's host is read; the subdomains an app's entitlements name each need their own, which this audit does not know.
- **The statements a file needs.** The Android page (ANDROID_ASSETLINKS) is about App Links; Digital Asset Links serve other relations too, such as `delegate_permission/common.get_login_creds` for shared sign-in credentials. A file without a `handle_all_urls` statement is therefore failed only when the profile says an Android app opens the site's links (the review of batch 1 found a correct credentials-only file failed). Apple's Associated Domains Entitlement page (read 2026-11-13) lists the services `webcredentials`, `applinks`, `activitycontinuation` (Handoff) and `appclips`; `authsrv`, which Apple's single sign-on extensions use, is accepted as well, so a file that serves only one of them is not failed. A Team ID is written in capitals; the profile's identifiers are compared without regard to letter case.
- **Not checked, and why.** Store listings and ratings are not read in this version. Google's Digital Asset Links API is not asked: the file is read from the site itself.

## Ai module: honest AI access and readiness (`checks/ai/`)

Which AI crawlers the site's robots.txt lets in, the training and grounding preferences the site states, whether its pages may be quoted in AI answers, and what a crawler that runs no script sees. Rule set 0.2.0; every source was read on 2026-11-14. The module is shown as a count, never as a score (`COUNTED_SCORES`: "N of M AI readiness checks passed"), and the report's AI search readiness section gives the counts that matter in words ("AI search crawlers that robots.txt lets read the start page: 5 of 6"). No check measures or promises visibility in AI answers, and no request goes to an AI vendor.

**The vendor data** (`plugin/server/data/ai-bots.json`, `plugin/references/ai-bots.md`, `util/ai-bots.js`). One row per robots.txt token: vendor, product, role (`search`, `mixed`, `training`, `control`, `user`, `policy`), whether the module counts it, the tokens it falls back to (Applebot follows the Googlebot group when robots.txt does not name it), what the vendor's page states about robots.txt and no more (`obeys` where it says the crawler follows, respects or obeys robots.txt; `documented` where it documents a robots.txt setting, what a disallow does or that its tags manage the crawler, without saying that; `may_ignore`; `ignores`). The review of 2026-11-14 found PerplexityBot and others marked `obeys` on pages that only document a setting; every row was re-read against its page. Amazon says Amzn-SearchBot follows the directives given to other search bots when robots.txt does not name it; which bots those are is not defined, so it is not modelled and the row says so, the vendor's IP list when its page names one, the vendor's page and `last_verified`. The file is checked when the plugin loads it. Every page is re-read at each release and at least monthly; a test fails when a row is more than 30 days older than the data date, or than the date of a dated release section in `CHANGELOG.md`. A row whose page could not be read gets `verified: false`: the report shows it marked, and no counted or scored check uses it. On 2026-11-14 every page was read (OpenAI's crawler page answered, unlike `openai.com`'s terms pages, which refuse automated reading); Bing's two help pages render only with JavaScript and were read in a browser. ByteDance publishes no page for Bytespider, so it is not listed.

**What it reads.** `CrawlResult.ai_robots` (`crawl/ai-robots.js`), worked out at the end of the crawl from the robots.txt of the start origin the crawl read anyway, so nothing is requested for it: for every token, whether `allowsAgents` lets it fetch the start page's final URL (its own group, then its fallbacks, then `*`, RFC 9309) and which group decided (`own`, `fallback`, `named` without a rule, `star`, `none`); the `__usage_ai-training` group alone, never `*` (draft-kelley-aipref-training-preference-signal-00); for each counted crawler that may read the start page, the pages it may not read among the first 200 html pages of the start origin (`blocked_pages`, at most 200 each); and the first 20 `Content-Usage` and `Content-Signal` values, clipped to 500 characters and read by `net/ai-prefs.js` in one pass without backtracking. Without `ai_robots` the checks that read it are skipped with the reason (`aiRobotsReason`), never run on nothing, and the run's training preference is `unknown`; an error while working it out is logged, recorded as `ai_robots_error`, and leaves the crawl and the other modules whole. Nothing is recorded when robots.txt answered a 4xx other than 404 and 410 (401, 403, 418…) or redirected too often: the crawler itself reads such an answer as no file (RFC 9309), but it can be a refusal of this crawler alone while a real AI crawler gets the file. The validation of 2026-11-14 found a site whose robots.txt answered 418 to Seekwide with its rules in the body; the run records the status (`ai.robots_refused`), and the notes and the report say that access was not judged. `PageRecord.ai` (`extract/ai.js`): the directives Bing reads (the robots and bingbot meta tags, and `X-Robots-Tag` lines for every crawler or for bingbot, where `ai-training:` and `ai-grounding:` are directives, not user agents; at most 50), the `span`, `div` and `section` elements with `data-nosnippet` (Google: "NOT VALID: not a span, div, or section") with the visible words inside them and whether the first `<h1>` is one, the `<script>` elements in the body, and an empty application mount element that is a child of `<body>` (`#root`, `#__next`, `#app`, `#__nuxt` with nothing but whitespace and comments in it). An unreadable record (a challenge, rate limiting) keeps the response headers of the kept list, which now name the CDN (`cf-ray`, `cf-mitigated`, `x-vercel-id`, `x-amz-cf-id`, `via`, `x-served-by`, `akamai-grn`, `x-nf-request-id`), and no content. `ctx.aiPolicy`: the AI policy the project profile states (`profile.ai_policy`: `allow_all`, `allow_search`, `block_all`; unset by default), used only when the profile's `site_url` is the audited site's own host (`util/profile-site.js`: lower case, without `www.` and a trailing dot, with the port; or, for a local crawl told where the project is deployed, that host), the rule the aso module's apps follow too: robots.txt is per host, so a policy for `www.acme.com` says nothing about `shop.acme.com`, and one for `127.0.0.1:4000` nothing about `127.0.0.1:3000`. Before the review of 2026-11-14 both used the site's organisation (its registered domain), and the profile store dropped `apps` and `ai_policy` on every write and read. `ctx.llmsTxt`: what the site answered at `/llms.txt` (below).

**The stated policy.** A block that matches the policy is not a finding; what contradicts it is. Unset, a block is reported as something to check against the owner's intent, never as a verdict, and the recommendation says how to record the policy.

**How /llms.txt is read** (`net/llms-txt.js`, through `net/site-files.js`, which the aso module's files use too). `audit_run` with the ai module and `check_llms_txt` (default true) requests the file once, after the app association files, for a crawl that no page refused. For a public site: robots.txt of the origin first (a file it disallows is `disallowed` and never requested), then one `GET` that accepts plain text and Markdown, reading at most `LIMITS.llmsTxtMaxBytes` (256 KiB), with redirects followed by hand, at most 3 steps, only where the crawl would go (the site's host on its port), each after its robots.txt; every request passes `guardFetch`, the host gates and the crawl's pacing. For a site on this machine the file is asked of exactly that origin, with loopback allowed for it alone; the deployed address is never contacted. The outcome is `found` for a 200 whose body is not empty and does not start with `<`, `not_found` for 404, 410, an empty body, an HTML page, or a redirect that ends at the start page (the research proposed calling the last two malformed; a site that answers every address with a page has no file, so they are not), `unverifiable` for anything else. Only the H1 (clipped to 200 characters), the number of Markdown links and the size are kept; the run records the address, outcome and status (`run.ai.llms_txt`).

- **Access matrix.** Vendors' own words, read 2026-11-14. OpenAI (OPENAI_BOTS): a site opted out of OAI-SearchBot is not shown in ChatGPT search answers, though it can still appear as a navigational link; disallowing GPTBot says the content should not be used for training; for ChatGPT-User "robots.txt rules may not apply". Anthropic (ANTHROPIC_BOTS): disabling Claude-SearchBot prevents indexing for search; disabling Claude-User prevents retrieval in answer to a user; a rule that names ClaudeBot wins over the shared preference, which Anthropic honours since 2026-10-30. Perplexity (PERPLEXITY_BOTS, moved to docs.perplexity.ai/docs/resources/perplexity-crawlers): PerplexityBot is managed with robots.txt and not used for foundation models; Perplexity-User "generally ignores robots.txt rules". Apple (APPLEBOT): Applebot follows the Googlebot rules when robots.txt does not name it, and Applebot-Extended refuses training only. Microsoft (BING_CRAWLERS, BING_GUIDELINES): robots.txt tells Bing's crawlers what to fetch; Bing and Copilot rest on the same crawling and index. DuckDuckGo (DUCKASSIST): disallowing DuckAssistBot takes effect after 72 hours. Google (GOOGLE_CRAWLERS): Google-Extended does not affect inclusion in Google Search, and Google intends to support the shared token in early 2027. The rows of Meta, Amazon, Mistral and Common Crawl are in the matrix and the policy check, not in the count.
- **Why a count.** Rule set 0.2.0, the user's decision of 2026-11-14, like the security headers: a few documented checks make a poor percentage, and a 0-100 "AI score" would read as a promise. The count is of scored checks that passed every unit; the report's section gives the unit counts.
- **Google's own statement** (GOOGLE_AI_FEATURES): a page must be indexed and eligible to be shown in Google Search with a snippet to appear as a link in AI Overviews or AI Mode, and "There are no additional requirements to appear in AI Overviews or AI Mode", nor special optimizations. The report quotes it next to the counts. GOOGLE_ROBOTS_META: `nosnippet` also prevents the content from being a direct input for AI Overviews and AI Mode, and `max-snippet` limits how much may be. GOOGLE_CONTROL_SHARE lists `data-nosnippet` and the Search Console "Search generative AI" control (rolled out worldwide on 2026-08-31), which cannot be seen from the site and is a manual check in the report.
- **Bing's new preferences** (BING_AI_PREFS, 2026-10-30): `<meta name="Bingbot" content="ai-training:disallow">` or `X-Robots-Tag: Bingbot: ai-training:disallow`, the same for `ai-grounding:disallow` and `ai-grounding:disallowextended`; training also through the shared robots.txt group; no site-wide grounding preference. Honoured from 2027-02-01; after 2027-03-01 NoArchive and NoCache are no longer read as training or grounding preferences. BING_DATA_NOSNIPPET: content marked `data-nosnippet` is excluded from snippets and AI summaries.
- **Draft syntax.** The shared token, `Content-Usage` and `Content-Signal` come from drafts or a vendor's own rule, which may change; hence `likely`, a low weight, and the draft's name in the evidence. No vendor was found that says it reads `Content-Usage` or `Content-Signal` yet.
- **Script-only pages.** Bing (BING_GUIDELINES) advises against hiding critical content behind client-side rendering and says content that cannot be reliably rendered may not be selected for grounding; OpenAI, Anthropic and Perplexity document nothing about running scripts, and a 2024 measurement (VERCEL_AI_CRAWLERS, secondary) found none of the major AI crawlers did; Google renders JavaScript. A page with only images and no text is not judged, since its content is not a script's.
- **What cannot be seen from outside.** A CDN or firewall can treat a real AI crawler differently from what robots.txt says. Seekwide never pretends to be one, so it is not tested; `ai.access.self_refused` says only that Seekwide's own crawler was refused. Cloudflare (CF_MIXED_USE, 2026-09-15, its blog only): Block and Block on pages with ads now also block Googlebot, Bingbot and Applebot; earlier Block settings for training were migrated to Disallow AI Training.
- **Not in this version.** Entity checks, agent readiness (form labels, PageSpeed Insights' experimental agentic category), server log import, the Search Console and Bing AI reports, and measured visibility in AI answers.

Rules without direct official support, kept on purpose and marked accordingly:

- `seo.content.thin`: Google states that it has no preferred word count. The check is `info`.
- `seo.h1.multiple`: no official rule limits a page to one `h1`. The check is `info`.
- `seo.canonical.missing`: Google recommends canonicals and does not require them. The check is `low` with weight 1.
- `seo.canonical.target_not_ok`: the documentation does not name this case; the finding is a measured fact (the canonical target does not answer 200, is not HTML, or is noindex).
- `links.depth.deep`: the page says Google uses the number of links needed to reach a page; the threshold of 4 is a rule of thumb. The check is `info`.
- `security.embeds.rare_host`: Google names scripts from an attacker's domain; a host used by one page only is a rule of thumb. The check is `info`.
- `security.content.spam_terms`: Google names pharmaceutical terms and counterfeit stores; the gambling terms and every topic word are this plugin's choice.
- `security.headers.*`: the rules come from MDN, the specifications and OWASP, not from Google; they protect visitors and do not affect ranking.
- `media.image.large_file`: no official page gives a size limit for one image; 500 KiB is a third of the total Lighthouse suggests for a page. The check is `info`.
- `media.image.legacy_format`: Lighthouse leaves out savings under 8 KiB; the 32 KiB floor applies web.dev's lowest WebP saving (25 %) to that number.
- `media.image.dimensions_missing`: web.dev documents missing sizes as a cause of layout shift, but whether a style sheet reserves the box cannot be seen without one. The check is `info`.
- `media.video.captions_missing`: whether a video has speech cannot be told from the page. The check is `info`.
- `media.image.alt_placeholder`: F30 names `spacer`, `image`, `picture`, numbers and file names; `photo`, `img`, `graphic`, `placeholder`, `untitled` and `alt text` are this plugin's additions of the same kind.
- `smo.og.image_preview_shape`: the platforms state how they show small images and recommend 1.91:1; the 15 % tolerance around it is this plugin's rule of thumb. The check is `info`.
- `smo.twitter.card_invalid`: X's card documentation is no longer online; the source is an archived copy. The check is `info`.
- `smo.profiles.sameas_missing` and `smo.profiles.rel_me_missing`: Google requires no property of organisation markup, and whether a fediverse profile lists the site cannot be seen from the site. Both are `info`.
- `smo.og.url_mismatch`: the list of session and campaign parameters is this plugin's; WhatsApp names the kind, not the names.
