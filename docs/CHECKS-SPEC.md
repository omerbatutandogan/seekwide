# Check specification (rules 0.1.7)

Every scripted check the plugin ships is defined here. The code in `server/src/checks/` implements this table exactly; `docs/checks.md` is generated from the code for users.

## How to read the tables

- **Unit**: what the check counts. It returns one result (pass or fail) per unit and nothing for anything else. The score uses the pass rate over units.
- **Fails when**: the condition for a `fail` result. Everything else in the unit set is a `pass`.
- **Sev / W**: severity and weight. Weight 0 means the check never changes the score; those are `info` checks based on rules of thumb.
- **Conf**: `confirmed` is a measured fact. `likely` is a strong signal that can have a legitimate exception.
- **Needs**: capabilities the audit must provide. The crawl provides `full_crawl`, `sitemap` and `robots`, and `live_site` when the site is not on this machine (`options.local` is not `true`); the external link check provides `outbound`; the check of image files (media module) provides `image_files`; the Core Web Vitals measurement provides `lab_data` and `field_data`. The engine skips the check otherwise, with the reason the collector gave.
- **Doc**: key into the reference list at the end.

Terms:

- *html page*: a record with status 200 and `is_html` (`ctx.htmlPages`).
- *indexable page*: a record with `indexability.indexable` (`ctx.indexablePages`).
- *effective canonical*: an entry in `page.canonicals` with `in_head: true` and a non-null `url`.
- *names the page itself*: a canonical URL equal to the page URL once the escapes of `!`, `'`, `(`, `)` and `*` are decoded (`sameCanonicalTarget`). Browsers send these characters as they are written, so a page linked as `/Today's_article` with a canonical to `/Today%27s_article` names itself; RFC 3986 does not make the two forms equal, so `normalizeUrl` keeps them apart (it decodes the escapes of unreserved characters only, so `%7E` and `~` are one URL). `canonical_elsewhere` and `seo.canonical.target_not_ok` use this comparison.
- *noindex*: `indexability.reasons` contains `noindex_meta` or `noindex_header`.
- *could not read*: `isUnverifiable(record)` is true. The site's firewall challenged the crawler, the site rate-limited it, or a redirect led to a URL that robots.txt disallows. That says something about the audit and nothing about the site, so such a record is never a unit and never a broken target.
- *start page*: `ctx.resolve(crawl.start_url)`.
- *tested page*: an entry of `ctx.vitals.pages`, one of the few pages whose Core Web Vitals were measured.

Evidence strings taken from a page are clipped with `clip()`. `related_urls` are sorted.

## Source files (repo mode)

A finding can carry `source: {file, line, route}`: the file of the user's project that the finding comes from. It is added after the checks ran, by `repo/sources.js` (ARCHITECTURE.md 4.12), only in an audit that was given a source folder, and only where the file can be determined. It is not part of a check's result, of the finding id or of the score, so the same crawl gives the same ids with and without it.

- `file`: path relative to the project folder.
- `line`: the line of the element in `file`, or null. Given for HTML files only.
- `route`: the Next.js route (`/blog/[slug]`) or the URL path.

No source is given to a site-level finding without a URL, to `seo.https.site_not_https`, `seo.https.not_enforced` and `seo.cwv.*` (they are about the server or about Google's measurements), or to a finding whose URL no file of the project answers. In a Next.js project that includes a URL that redirected or answered 404, and a URL that only a route with a dynamic segment matches unless it answered 200.

## A local site that names its deployed address

A project's pages name the address the site is deployed at, in canonical links and in the sitemap. Audited on `http://localhost:3000`, such a page would not be indexable (`canonical_elsewhere`), so every check whose unit is an indexable page would skip it, and `seo.canonical.cross_host` would fail on it. When a crawl of a local site is told that address (`site_url` on `crawl_start`; ARCHITECTURE.md 4.5), a canonical URL and a sitemap entry on exactly that origin are recorded as the same path on the local server. The checks themselves do not change and do not know about it: they read the record. `href` in a canonical keeps what the page sent, so `seo.canonical.relative` still judges the page's own text. Finding ids are unchanged, because they are built from the page's URL, which is the local one either way.

## Fixes and their verification

`/seekwide:fix` (ARCHITECTURE.md 4.13) plans changes for the findings of nine checks: `seo.title.missing`, `seo.title.duplicate`, `seo.title.multiple`, `seo.meta_description.missing`, `seo.meta_description.duplicate`, `seo.meta_description.multiple`, `seo.canonical.missing`, `seo.social.og_incomplete` and `seo.sitemap.missing`. A fix never changes a finding, an id or a score; only the next audit does. When that audit verifies fixes, a finding that is gone counts as closed only if its check looked at the same unit again. The unit of each of the nine checks is recorded next to the fix (`FIXABLE_CHECKS` in `repo/fixes.js`), and a test holds that table to what the checks do. Change it together with the check.

Notes:

- Duplicate checks (`seo.title.duplicate`, `seo.meta_description.duplicate`, `seo.content.duplicate_body`) return a result for every page in the unit set. Failing results give the size of the group in `evidence` and list its other pages in `related_urls`. Evidence never copies page text in bulk: lists in evidence hold at most five entries.
- `seo.title.too_long` estimates width with Arial advance widths (units per em of 2048) at 20 px. Characters without a table entry count as 1139 units; CJK and other full-width characters count as 2048. Evidence: `{observed: {characters, estimated_px}, expected: '580 px or less'}`.
- `seo.canonical.multiple`: compare normalized URLs. A header canonical and a link element that name the same URL are not a conflict.
- Headings and visible text (`word_count`, `text_hash`, `text_excerpt`) leave out the fallback of a React Suspense boundary that the page's own streaming script completes: the streamed content that replaces it is in the document too, so counting both counted a page's headings and text twice (a login page had two identical `h1`). See *Revealed by the page's own script* in the security module for how such a boundary is recognised. The fallback's links and images are kept, because a crawler that runs no script sees them.
- Duplicate checks say "1 other page uses" and "2 other pages use", with the verb in agreement.
- A check that needs `sitemap` and is skipped because sitemap files were found but none gave URLs says why: the site refused the crawler's request (with the status), or the files gave no URL that could be read.
- Selectors: `head > title`, `meta[name=description]`, `link[rel=canonical]`, `h1`, `html`, `meta[name=viewport]`. Site-level checks use no selector.
- `http_probe` is null, so `seo.https.not_enforced` has no unit, when the http request failed or was refused (429 or a bot challenge), when robots.txt does not allow it, or when the site is on a port other than the default.
- A redirect that leads to a file and not a page (judged by its URL) is followed with a `HEAD` request. When the HEAD fails or answers 400 or above (429 and bot challenges excepted), a `GET` limited to 16 KB is sent and its answer is used. The answer sets the redirect's `final_status`, so `seo.redirect.broken` and `links.internal.broken` see it, but the file gets no record of its own.

### Core Web Vitals (`checks/seo/cwv.js`)

These checks read `ctx.vitals`, which `vitals/measure.js` collects from two Google services before the checks run (`docs/ARCHITECTURE.md`, 4.11). The checks themselves do no I/O.

| Id | Unit | Fails when | Sev / W | Conf | Needs | Doc |
|---|---|---|---|---|---|---|
| `seo.cwv.field_lcp` | The site's origin when the Chrome UX Report has a Largest Contentful Paint value for it (`url` = null, `selector` = `origin`), and each tested page it has a value for | the 75th percentile is above 2500 ms | medium / 3 | confirmed | field_data | LCP |
| `seo.cwv.field_inp` | The same, for Interaction to Next Paint | the 75th percentile is above 200 ms | medium / 3 | confirmed | field_data | INP |
| `seo.cwv.field_cls` | The same, for Cumulative Layout Shift | the 75th percentile is above 0.1 | medium / 3 | confirmed | field_data | CLS |
| `seo.cwv.lab_lcp` | Each tested page with a lab Largest Contentful Paint value | the value is above 2500 ms | low / 2 | likely | lab_data | LIGHTHOUSE_LCP |
| `seo.cwv.lab_cls` | Each tested page with a lab Cumulative Layout Shift value | the value is above 0.1 | low / 2 | likely | lab_data | CLS |
| `seo.cwv.lab_tbt` | Each tested page with a lab Total Blocking Time value | the value is above 200 ms | low / 1 | likely | lab_data | LIGHTHOUSE_TBT |

Notes:

- **Tested pages.** Measuring is slow and rate-limited, so only a few pages are measured: 3 by default, at most 10. The start page comes first when it is indexable. The other indexable pages are grouped by `templateSignature` (first path segment and number of segments), and one page is taken from each group, largest group first (then the group whose pages are closest to the start page, then by signature). Inside a group the page with the smallest `depth` is taken, then the first by URL; a page found only in the sitemap comes last. A slow template shows on every page that uses it, so one page per group says the most per request. When more pages are asked for than there are groups, the groups are gone through again for their next page. Each tested page records why it was chosen.
- **Field data** is what real Chrome users on phones experienced over the last 28 days, from the Chrome UX Report API (`formFactor: PHONE`). The value compared is the 75th percentile, as Google's own assessment does. Phones are used because the lab test also emulates a phone and because the documented thresholds are the mobile ones. The origin record covers every page of the site; a tested page has its own record only when it has enough visits. An origin or page the report has no data for is not a unit: that says the page has too few visits from Chrome users, nothing about its speed.
- **Lab data** is one simulated page load by PageSpeed Insights (`strategy: MOBILE`, `category: PERFORMANCE`), which runs Lighthouse on an emulated mid-range phone. Times are rounded to whole milliseconds and the layout shift score to three decimals before they are compared. A page PageSpeed Insights could not test is not a unit.
- **Interaction to Next Paint has no lab check.** A page load without a user has no interactions, so Lighthouse cannot measure it. Total Blocking Time is the lab stand-in; it is not a Core Web Vital, which is why it weighs least.
- **Confidence.** A field value is a measured fact about real visits, so the field checks are `confirmed`. A lab value comes from one simulated load and changes from run to run, so the lab checks are `likely`: a value near the threshold is worth a second run.
- **When the data is missing.** `field_data` is provided when the Chrome UX Report API answered for the origin or for a tested page, with a record or with "no data". Without a Google API key it is never provided, because that API requires one. `lab_data` is provided when PageSpeed Insights returned values for one or more tested pages. When Google refuses a request (no quota, a key it does not accept), does not answer in time, or the site is on the user's own machine (or the crawl does not record that it is not), the capability is missing and the checks that need it are skipped. The skip reason is the collector's plain statement of what happened. A missing capability never fails the audit.
- Evidence, field: `{observed: {p75_ms, rating, good_loads}, expected: 'A 75th percentile of 2500 ms or less', detail}`. For layout shift, `p75` replaces `p75_ms`. `rating` is `needs improvement` or `poor` (above 4000 ms, 500 ms and 0.25). `good_loads` is the share of page loads inside the good range, as a percentage, and is left out when Google's histogram does not use the same boundary. `detail` names the form factor, the collection period, and whether the value is for the whole site or for the page.
- Evidence, lab: `{observed: {lcp_ms | cls | tbt_ms, rating}, expected, detail}`. `rating` uses 4000 ms, 0.25 and 600 ms as the upper bounds of "needs improvement", the mobile bounds Lighthouse documents. When Google was redirected and tested another URL, `detail` names it: the finding stays on the tested page, because that is what a phone visiting it gets.
- Thresholds live in `vitals/thresholds.js`, so the checks and the reports cannot disagree.

A link in a menu or footer is one fix however many pages repeat it.

A redirect that leaves the site has `final_external: true` and `final_status` 0; its destination is checked with the external links, and a broken one is reported by `links.outbound.broken` on the page that links to the redirecting URL.
- External link results: `broken` means 404, 410, or a host name that does not exist. A site that refuses automated requests, a robots.txt rule, a timeout or a temporary DNS failure gives `unverifiable`, which is not a unit.
- `links.orphan.sitemap_only`: build the set of linked URLs from every internal link on every html page, adding `ctx.resolve(link.url)?.url` so a link to a redirect counts for its destination. A link from a page to itself does not count.
- Selectors of the form `a[href="…"]` escape `\` and `"` inside the href.
- `links.anchor.uncrawlable`: Google's page (LINKS, read 2026-11-12) asks that the URL in an `<a>` element resolve to an actual web address that its crawlers can send requests to, and names `javascript:` hrefs as not recommended; both of its examples open a page (`goTo('products')`, `window.location.href='/products'`), and it says Google cannot reliably extract URLs from elements with no href or from script events. One rule covers every case: a link fails when what it opens is not in its href as a web address. A `vbscript:` URL is a script like `javascript:`, and a `data:` URL carries its document inside the link, so neither is an address a crawler can request. A script that only prints, goes back or does nothing, on an element with no `onclick`, opens no page at all: it is a control that looks like a link (a print button, a back button, a menu toggle), there is no page for a crawler to find, and it is not a unit. With an `onclick` or another script handler, the handler does whatever the link does, as on an element with no href, so it fails. Known gap: a handler on an element around the link (a delegated click handler) is not seen, so such a script link with no destination is not a unit. `mailto:`, `tel:` and other schemes that hand the link to another program open no page, so they are not units that fail.
- `links.internal.nofollow`: Google's page (QUALIFY_LINKS, read 2026-11-12) says that links marked nofollow will generally not be followed, and that for links within your own site the robots.txt disallow rule is the way to stop a fetch. A page is withheld only when every link to it on the page is nofollow: a nofollowed copy of a link the page also has without nofollow (a mobile menu that repeats the footer) withholds nothing. Share, comment-reply, cart and export links carry a query string and are actions, not pages to index; a link to a fragment of the page itself goes nowhere new; a target robots.txt disallows already gets the treatment Google recommends. Known gap: a page with a query string that is a real page (a pagination URL `?page=2`) is not a unit.
- `links.internal.redirect`: Google's page on HTTP status codes (HTTP_STATUS, read 2026-11-12) treats 301 and 308 as a strong signal that the target should be processed and 302, 303 and 307 as a weak one, and its site-move page (SITE_MOVE, read 2026-11-12) asks to update internal links to the new URLs. A temporary redirect is often meant: a login page for an app entry, a regional edition, an add-to-cart action. So such a finding is `likely`, and a temporary redirect to a page that carries the link's own address in its query (a login that sends the visitor back) is not a unit. A chain with any permanent hop stays `confirmed`.
- `links.anchor.empty` and `links.anchor.generic`: Google's page (LINKS, read 2026-11-12) marks empty link text and generic text such as "click here" as bad and uses an image's `alt` and, for an empty link, its `title` as anchor text; it says nothing about `aria-label` or fragment links. A link marked `aria-hidden` is left out of what screen readers read, and sites use it for copies (a heading's permalink, a card's image link beside its title link); a link into the page itself leads to no other page. When another link on the page to the same address is named, Google has anchor text for that address and a visitor has a named link to it, so an unnamed or generic copy passes. Known gap: a screen reader user who reaches the unnamed copy first hears no name; that is an accessibility finding, not one about crawling.
- Generic-anchor list (compared after lower-casing and removing punctuation): English "click here", "here", "read more", "more", "learn more", "this", "link", "this link", "this page", "continue", "continue reading", "details", "more info", "more information"; Turkish "tıklayın", "buraya tıklayın", "burada", "buraya", "devamı", "devamını oku", "daha fazla", "detaylar", "incele"; German "hier", "hier klicken", "mehr", "weiterlesen", "mehr erfahren"; Spanish "aquí", "haz clic aquí", "leer más", "más", "ver más"; French "ici", "cliquez ici", "lire la suite", "en savoir plus", "plus".

## Security module (`checks/security/`)

Signs that a site was hacked or misused, measured from outside, and the security headers of its start page. Google warns about or demotes hacked sites, and a hacked site is usually built to hide the hack from its owner, so the module looks for what the owner does not see.

**What it looks at.** Only the responses the crawler fetches anyway: the same pages, with the same user agent, robots.txt and pacing. It requests no path the site does not link to or list (no `/wp-admin/`, `/.env` or `/.git/`), never tries an exploit, and never sends a second request with other headers to look for cloaking. That has a limit that every report states: many hacks show their spam only to Google's crawler or to visitors who come from Google, so a clean result does not prove a clean site. Search Console's Security issues report is where Google says what it found.

**The signals** are read while a page is extracted (`extract/security.js`, `extract/concealment.js`, `extract/terms.js`, `extract/security-headers.js`) and stored as `PageRecord.security`. A record without it (a crawl made before the module existed) is not a unit of any security check.

- *Hidden by its markup*: an element, or an element above it, that has the `hidden` attribute (not `hidden="until-found"`, and not together with an inline `display` value other than `none`), or an inline `style` with `display: none`; `visibility: hidden` or `collapse` (undone by `visibility: visible` further down); a font size of 1 px or less (undone further down by an absolute font size, or by any element with a `class`, through which a style sheet may set one; `em`, `%` and `inherit` stay 0); an offset that moves the box 1000 px or more to the left or up, off the page (a negative `left` or `top`, or a positive `right` or `bottom`, with `position: absolute`, `fixed` or `relative`; a negative `margin-left` or `margin-top`; or the x or y of a `translate` in `transform`; em and rem count as 16 px, and percentages and viewport units do not count, because an off-canvas menu moved by -100% is a menu); or a width or height of 2 px or less with `overflow: hidden` or `clip`, no padding along that axis (the `padding` shorthand read side by side, the longhands and the logical properties), and no `clip` or `clip-path`. Style sheets, classes and scripts are not read, and at most 20,000 characters of a `style` attribute are. Not counted: `opacity: 0`, which animation libraries use as the start state of content they fade in; `text-indent`, which moves the text of a box that is still there (a logo drawn as a background image); and the 1 px box with `clip`, the usual way to keep text for screen readers.
- *Built to be opened*: content a visitor can reveal, which Google allows (tabs, accordions, menus, pop-ups): a hiding element with `role` `dialog`, `alertdialog`, `menu`, `menubar`, `tabpanel`, `tooltip` or `listbox`, or with a `popover`, `aria-modal`, `x-show`, `x-cloak` or `v-show` attribute; one whose previous element sibling is a disclosure control (a `<summary>`, or an element with `aria-expanded` or `aria-haspopup`); and one whose `id` a control on the page names, anywhere in the document: in `aria-controls`, `popovertarget` or `commandfor`, as the `href="#id"` of a link, or, with or without `#`, as the value of one of `data-target`, `data-bs-target`, `data-toggle-target`, `data-tab`, `data-tab-target`, `data-src`, `data-modal`, `data-modal-target`, `data-popup`, `data-open`, `data-reveal-id`, `data-micromodal-trigger`, `data-controls`, `data-panel` and `data-fancybox-src` (at most 20,000 such values are collected; the others always are). A plain button or link right before an element does not make it openable: the last element of a page is often a back-to-top button, and injected content often comes right after it. A hidden element keeps every element that hides it, up to four of each kind, and a link counts as hidden when one of them is not built to be opened.
- *Revealed by the page's own script*: React's streaming server rendering (React 18 and later; the Next.js App Router) sends a Suspense boundary's content after the rest of the page in `<div hidden id="S:n">`, leaves `<!--$?--><template id="B:n"></template>` (the fallback) `<!--/$-->` where it belongs, and moves it there with an inline call as the page loads. A hidden element counts as built to be opened, for its own `hidden` attribute only, when all of this holds (`extract/react-stream.js`): it is a segment of the shape React writes, with no inline `style`: a `<div hidden>` or `<table hidden>` with the segment's id, or, in React's table modes, the `<table hidden>` around a `<tbody>`, `<tr>` (inside the `<tbody>` the parser adds) or `<colgroup>` with the id (since rule set 0.1.7; React's script moves only the children of the element with the id, so any other element, such as a link that is itself hidden, is never shown); an empty `<template>` with the other id of the call comes before it in the document, in a place the page renders (since 0.1.7: not in `<head>`, and not inside a `<video>`, `<audio>`, `<canvas>`, `<object>` or `<datalist>`, whose content is fallback content); and after it an inline script of a JavaScript type, not `nomodule`, has as a top-level statement (at the start of the script or after a `;` outside any bracket) a call `$RC("B:n","S:n")` or `$RR("B:n","S:n",…)` (the template's id, then the element's) or `$RS("S:n","P:n")` (the element's id, then the template's), with that function defined (`$RC=function`, or `function $RC(`) by a top-level statement of an inline script before the call. The script is read with comments removed and string literals set apart, so a definition or call in a comment, inside a string, in a block (`if (false) {…}`) or in an expression (`a && $RC(…)`) does not count. For `$RC` and `$RR` the template must also follow a `<!--$?-->` comment and the boundary must be closed by `<!--/$-->`, with nested boundaries counted. When ids repeat, the first element with the id counts, as for `getElementById`, whatever its namespace (since 0.1.7, an earlier SVG element with the id takes it, and the segment stays hidden). Every other way of hiding inside, on or above the segment still counts. The page's script moves the segment's content to its template, so the content counts as hidden when an element hides it in either place: above the template (a boundary inside a `display: none` box) or above the segment where it is served. The text of the replaced fallback still counts for spam terms and writing systems. To keep the work linear, at most 100,000 sibling nodes are looked at in all to find a document's fallbacks; a boundary past that is not read as revealed.
- *Another site*: a host whose registered name differs from the audited site's (`acme` in acme.com, acme.de and shop.acme.co.uk, under the usual second-level endings of country domains; `siteLabel` in `util/site-name.js`), and a link that is not a share link. A *share link* goes to a known share or messaging service and its query, decoded, names the audited site's host as a whole name (`facebook.com/sharer/sharer.php?u=https://acme.com/post`; `isShareLink` in `extract/share-links.js`). The services, matched by exact host without `www.` (a blog on tumblr.com is not Tumblr's share page), are facebook.com, m.facebook.com, twitter.com, x.com, linkedin.com, pinterest.com, wa.me, api.whatsapp.com, web.whatsapp.com, t.me, telegram.me, tumblr.com, vk.com, reddit.com and mastodonshare.com, from the share URLs these services document for websites (read on 2026-11-12; Reddit's documentation refused to be read by a script, so its entry rests on its submit page) and the share menus of the validation pages; an e-mail link is not a web address and never counts. A link to any other host is never a share link, whatever its query holds: before rule set 0.1.7 any link whose query named the site was left out, so an injected `spam.test/pills?ref=acme.com` or `spam.test/pills?u=https://acme.com/` was never reported. On the 205 validation pages of 17 sites saved on 2026-11-12, every share link that named the site went to a service on the list, and the change adds or removes no finding; links that named the site in other ways (a Google site search, a donation campaign, a calendar subscription) now count as visible links to their hosts. Under a shared hosting domain, where each customer gets a host of its own (acme.vercel.app, acme.github.io), the registered name is the customer's whole host: another customer's host (spam.vercel.app), the service's own site (vercel.com) and any other domain are other sites, and only the host itself and its subdomains (preview.acme.vercel.app) are the site's own, in both directions (spam.vercel.app is another site on vercel.com too). The shared hosting domains are a short list taken from the private section of the Public Suffix List, read on 2026-11-12: amplifyapp.com, appspot.com, azurewebsites.net, blogspot.com, carrd.co, cloudfront.net, deno.dev, firebaseapp.com, fly.dev, framer.app, framer.website, github.io, gitlab.io, herokuapp.com, myshopify.com, netlify.app, now.sh, onrender.com, pages.dev, repl.co, replit.app, surge.sh, vercel.app, web.app, webflow.io, wixsite.com, wixstudio.io and workers.dev. A hosting service that is not on that list (wordpress.com, and the country domains of blogspot, which the list no longer has) is compared by its name like any site, and so are the list's suffixes of three or more labels, such as the regional S3 endpoints (`bucket.s3.eu-west-1.amazonaws.com`), which only two-label entries are looked up for. Links to the same organisation's other domains and share links are left out of `hidden_links` and `visible_hosts`. The cost of the same-name rule was measured on 2026-11-12 on the 205 pages of 17 sites saved by the validation: it made the site's own 6 sister domains (wordpress.net, wordpress.com and wordpress.tv on wordpress.org, gov.scot and gov.wales on gov.uk, one more on yoast.com), every link to them visible, so it neither hid a hidden link nor prevented a false alarm there. It stays: it keeps a hidden country or language menu that links to acme.de from being reported on acme.com, and spam on a domain with the site's own name under another ending (acme.ru on acme.com, or any `*.gov.<ending>` on gov.uk, whose registered name is `gov`) needs a domain registered against that one site, which is a known gap.
- *Concealed link*: a link to another site that is hidden by its markup, or whose whole text is one punctuation character (`\p{P}` or `|`) with no `aria-label` and no `title`, which is Google's example of a link on one small character. Every other link to another host is visible, and its host is one of the page's `visible_hosts` (at most 1000). `hidden_links` holds, for each host the page links to only in concealed links, the first such link and their `count` (at most 200 hosts); its `index` is the link's position in `links`.
- *Embed*: a `<script src>` (of a JavaScript type) or an `<iframe src>` on another host. A frame is *hidden* when its width or height is 2 px or less (the inline style wins over the `width` and `height` attributes), or when its markup hides it as above. A media or map player (a path segment `embed` or `player`, or a host that starts with `player.`) hidden only by an element around it is waiting to be opened (a video lightbox) and is not hidden; one whose own markup hides it is.
- *Spam terms*: matches, as whole words in lower-cased text, of the lists below in the whole visible text (text hidden by CSS is part of it, the headline too) and the words of external link URLs. Titles and meta descriptions are not counted, because they repeat the headline. *Topic words*: the spam terms and the topic words of a category in the titles, meta descriptions and headings.
- *Writing systems*: letters per system in the first 50,000 characters of the visible text: Latin, Cyrillic, Greek, Arabic, Hebrew, Devanagari, Thai, Hangul, Chinese and Japanese characters (one system), and `other` for every other letter. The *site's systems* are those with 5% or more of the start page's letters, known when the start page has 200 letters or more. A page's *foreign system* is the largest system that is not Latin, not `other` and not one of the site's, with at least 100 of the page's letters and 30% of them.
- *Security headers*: read from the full response headers the way browsers read them (below).

Site-level checks use the *start page* (`ctx.resolve(crawl.start_url)`) when it is an html page with the signals; without one they have no unit. Text from a page that goes into evidence is clipped.

Notes:

- **Why a hidden link counts only when its site is not linked visibly, and not when it is built to be opened.** Google's spam policies name text positioned off-screen, a font size or opacity of 0 and a link on one small character, and say that accordions, tabs, sliders, tooltips and text for screen readers are not a violation. Google describes content injection in hacked sites as hidden links or hidden text added through CSS or HTML. Such links are most often hidden with `display: none` or an off-screen box, while menus, tabs and pop-ups hide links with the same markup. So an element built to be opened does not hide, and a concealed link counts only when no visible link on the crawled pages goes to the same site (a menu hidden on one screen size links visibly somewhere else). Opacity is the one technique Google names that is not read, because animated pages start most of their content at opacity 0. White text on a white background and text behind an image need rendering and are not measured. Known gaps: an offset of less than 1000 px, spam inside `<noscript>` (text, for a parser that runs scripts), a hiding element whose `id` happens to be named by an unrelated control (a skip link to `#footer`), and hiding through a style sheet. Known false positives that remain: a dropdown that a plain button opens without `aria-expanded`, holding links to other organisations' sites that are linked nowhere visibly, and slides of a slider that are not marked as tab panels; `likely` and the evidence's hiding element are there for them. When such a block carries spam terms, `security.content.spam_terms` reports the page as well, because it counts hidden text and link addresses.
- **Spam terms.** Google's Security issues report says injected spammy text "may contain pharmaceutical terms", and its guide to the Japanese keyword hack describes links to stores of counterfeit brands. The gambling list is this plugin's addition, from the same kind of spam (no Google page names it). Lists, matched as whole words with any run of spaces between words (the Turkish İ and ı match as i):
  - pharma: viagra, cialis, levitra, kamagra, sildenafil, tadalafil, vardenafil, online pharmacy, canadian pharmacy;
  - gambling: online casino, casino online, casino bonus, no deposit bonus, slot gacor, situs slot, judi online, judi slot, judi bola, situs judi, agen judi, togel, bandar togel, sbobet, maxwin, slot88, deneme bonusu, bahis siteleri, casino siteleri, canlı bahis, kaçak bahis;
  - counterfeit: replica watches, replica handbags, replica rolex, fake rolex, cheap jerseys, cheap nfl jerseys, louis vuitton outlet.
  Phrases that ordinary pages use are left out: "slot online" (booking a delivery slot online), "free spins" (game guides), and the names of real outlet stores.
  Topic words, which make a category part of the site's subject when the start page's title, description or headings have one of them (or a spam term of the category): pharma: pharmacy, pharmacies, drugstore, apotheke, eczane, farmacia, pharmacie, medicine, medicines, medication, medications, clinic, urology, sexual health, health, medical, hospital, doctor, doctors; gambling: casino, casinos, gambling, betting, poker, slots, lottery, bahis, kumar, judi, apuestas, wetten; counterfeit: replica, replicas, watches, handbags, fashion, jerseys, outlet. The counts are made when the page is read, because the record keeps only an excerpt of the text; a change to the lists applies to crawls made after it.
- **Writing systems.** Google's guides to the Japanese keyword hack and the gibberish hack describe spam pages in another language, often in folders the site does not link to; such pages are found only when a link or the sitemap leads to them. Languages are mapped to systems by their primary subtag (`ja`, `zh`, `yue` → Chinese and Japanese characters; `ko` → Hangul; `ru`, `uk`, `bg` and the other Cyrillic languages; `el`; `ar`, `fa`, `ur` and the other Arabic-script languages; `he`, `yi`; `hi`, `mr`, `ne`; `th`; `sr`, `kk`, `uz` in either of their two systems), or by a script subtag (`sr-Latn`, `zh-Hant`) when there is one; any other language is Latin. Latin script is never a foreign system: product names, code and English pages on a site in another script are common, and spam in Latin script is what `security.content.spam_terms` looks for. Shares are counted in letters, and one Chinese or Japanese character carries about as much as a short English word, so a spam page in Japanese inside the site's English template can have fewer than half of its letters in Japanese; hence 30% and not a majority.
- **Two results: a score and a count.** The header checks count toward a result of their own, `security_headers` (`score_group` on the check, `SCORE_GROUPS` in `config.js`), and the module's `security` score covers the five checks for signs of a hack. A clean site with three headers missing scored 79 to 83 when the two were one number, which a reader takes for a security problem with the site; the headers protect visitors and say nothing about a hack. Since rule set 0.1.7 the headers are given as a count, not a score (`COUNTED_SCORES` in `config.js`): `count` is how many of the scored header checks that looked at the start page passed, out of how many did (`{passed: 0, of: 3}`, or 2 on an http site, where Strict-Transport-Security does not apply), `score` is null, and `note` says it in words ("0 of 3 recommended headers set. A count, not a score."). As a score, a site without the three headers got "Security headers 0/100" (example.com did), which reads as a verdict on the site; the count says what was measured, and it is as deterministic. `audit_run`, both report formats, the run index (`counts`), the comparison of two runs (`from_count`, `to_count`, and `delta` as the change in the count) and the skills give the count. A run stored before 0.1.7 keeps its score and is shown with it. A report shows the two as two lines ("Security" and "Security headers"), and the findings of both stay in the `security` module. Without the deployed site (a local crawl) the headers have no count (`count: null`), with the reason in `note`, and the security score keeps full coverage.
- **React streaming.** On nextjs.org the whole footer arrives as a streamed boundary, so its links to other sites were "hidden by the hidden attribute" on 22 of 25 pages, with a security score of 75. The page's own script reveals them as it loads, so they are not hidden from visitors. The exemption needs every part of the pattern React writes, in document order, and excuses only the segment's own `hidden` attribute. Known gap: a page that forges all of it with a script that does nothing (defines `$RC` as an empty function, as a top-level statement) keeps such a block hidden from visitors and from this check; that takes markup written against this rule, not the hiding that injected spam uses (`display: none`, an off-screen box), which still counts inside and around a boundary and where its content is moved. A review of 2026-11-12 found that the first version also accepted the pattern in comments, strings and dead code, and judged a segment only where it is served; both are closed. Three ways to close the gap were measured on 2026-11-12 against the 19 nextjs.org and vercel.com pages saved by the validation, the excerpts kept from them, and forged pages, and none was kept: requiring React's own runtime (its exact code, or a body that looks elements up by id) stops an empty `$RC`, but a page that copies React's runtime and adds one statement that makes it inert (a `throw` before the call, a no-op `requestAnimationFrame` or `$RB.push`) still passes, and an exact match would lose the exemption, and bring the false alarms back, with every React release that changes the runtime's code; requiring other React or Next.js markers (`<!--$-->`, `self.__next_f`) stops nothing a forger cannot add in one line, and the Next.js markers would fail React streaming on other frameworks; reporting, as a weaker finding, every link of a revealed block to a site no visible link goes to reports the footers of nextjs.org and vercel.com, the false alarm the exemption exists for. What remains: the spam-term check reads such a block like any other part of the page, so it reports there what it would report anywhere else (two or more listed terms of a category the start page is not about), with the same limits: a single term, terms off its lists, a term written with an invisible character or a look-alike letter, a term only in an `alt` or `title`, and two link texts that touch without a space ("viagra" and "cialis" read as "viagracialis") are not counted. A review of 2026-11-12 also found four ways a block could take the exemption without the forgery, all closed in 0.1.7: a segment that is itself a link (React's script removes it), a template in `<head>` or in a video's fallback content, and an earlier SVG element that takes the segment's id; and one false alarm, React's table modes (`<table hidden><tbody id="S:0">`), now read as React writes them.
- **One hidden link.** A finding with one hidden link says that it can be the site's own (a partner's logo in a block no longer shown) and asks whether someone on the owner's side added it; the recommendation names that case before the hack. The finding, its severity and its weight do not change.
- **Embeds.** Google's guide to sites hacked with malware describes injected `<iframe>` elements, often sized to zero and hidden with CSS, and `<script>` elements that load from the attacker's domain. A tracking tag that uses a 1×1 frame outside `<noscript>` is a legitimate exception, hence `likely`. A frame inside a responsive wrapper (`height: 0` with a padding that gives the box its height) is visible. Content inside `<noscript>` is text for the parser (scripting is on), so the frames of tag managers there are not seen. Rarity has no official threshold, so `security.embeds.rare_host` is `info`; on a crawl of 25 pages every video, map or form embedded on one page is used by one page (all 14 such findings of the validation of 2026-11-12 were), so it needs 50 pages.
- **Headers are not Google ranking factors.** Google's page experience documentation lists HTTPS but no security header, and Google stated in its Search Central office hours of June 2023 that the HSTS header does not affect Search. The header checks protect visitors, which is why they are `low` or `info`. They need `live_site`: a crawl of a server on this machine (`options.local: true`) says nothing about the headers of the deployed site, so they are skipped there with that reason.
- **How headers are read.** Strict-Transport-Security: only the first header counts; it is invalid (ignored) when a directive appears twice, when `max-age` is missing or not a number, or when a directive breaks the grammar; unknown directives are ignored (RFC 6797, 6.1 and 8.1). X-Content-Type-Options: the first comma-separated value must be `nosniff` (Fetch). Clickjacking: an enforced Content-Security-Policy header with `frame-ancestors` overrides X-Frame-Options, a source list allows a framer that matches any one source, and a framer must pass every enforced policy; `frame-ancestors` in a `<meta>` policy is ignored, and so is X-Frame-Options in a `<meta>`; one X-Frame-Options value other than `deny` or `sameorigin` counts as absent, and several values that include `deny`, `sameorigin` or `allowall` block framing (HTML, 7.7; CSP 3, 6.4.2). Content-Security-Policy-Report-Only enforces nothing. Referrer policy: the last valid `<meta name="referrer">` anywhere in the document (legacy values `never`, `default`, `always` and `origin-when-crossorigin` mapped as HTML does; an invalid one changes nothing), else the last valid token of the Referrer-Policy header; with neither, browsers use `strict-origin-when-cross-origin`, which sends other sites the origin only, so a missing policy passes.
- **Not checked, and why.** Cloaking and sneaky redirects: finding them needs a request that pretends to be Google or comes from a Google search, which this crawler never sends. Outdated or vulnerable WordPress core, plugins and themes: the plugin version in a `?ver=` parameter is often WordPress's own version, the WordPress.org version APIs publish no terms of use, and the vulnerability databases that allow use by agencies need a key of each user's own; this is left for a later version. Admin accounts, file integrity and backups cannot be seen from outside; the report lists them as things to check by hand.

## Media module (`checks/media/`)

Images and video: text alternatives, the space an image takes before it loads, lazy loading, the image files themselves, captions, and video structured data. Rule set 0.1.6; the own-site rule changed in 0.1.7. Audit only: no fix exists for these findings yet.

**What it reads.** Most checks read what extraction records about `<img>`, `<video>`, embedded video players and JSON-LD (`extract/media.js`, `extract/media-image.js`, `extract/jsonld.js`). A record made before the module existed has no `videos` list (`hasMedia`) and is not a unit of any media check, because it lacks the fields the exceptions below need. The `image_files` checks also read `ctx.imageFiles`, which the audit collects before the checks run (below).

Terms:

- *rendered image*: an `<img>` on an html page that is not hidden by its own markup (the `hidden` attribute, other than `hidden="until-found"`, or `display: none` in its inline `style`) and is not a tracking pixel or a spacer (a `width` or `height` of 1 pixel or less, as an attribute or as an inline `style` in `px` or a unitless 0). Images inside `<noscript>` are text for the parser and are never recorded (ARCHITECTURE.md 4.6).
- *content image*: a rendered image that is not in the page's frame: not inside `<nav>` or `<aside>`, not inside a `<header>` or `<footer>` that is outside every `<article>`, `<main>`, `<section>`, `<aside>` and `<nav>` (the page's own header and footer, as ARIA maps them to `banner` and `contentinfo`), and not inside an element with the role `banner`, `navigation`, `contentinfo` or `complementary`. Logos, icons and badges live in the frame.
- *exposed image*: a rendered image that is not marked `aria-hidden="true"` (it or an element around it) and has no `role` of `presentation` or `none`. ARIA in HTML allows those two roles on an `<img>` without `alt`; they say the author removed the image from what assistive technology reads, as `alt=""` does.
- *spoken video*: a `<video>` on an html page that is not hidden by its own markup, not `aria-hidden`, not `muted`, and not `autoplay` without `controls`. A muted or autoplaying video without controls plays without sound in browsers (autoplay with sound is blocked), which is how background and decorative videos are made.
- *checked image file*: an entry of `ctx.imageFiles` (below). Its finding's `url` is the first html page, by sorted URL, that shows the file in a rendered image, `selector` is `img[src="<raw src>"]` of that element, and `related_urls` are the other pages.
- *own site*: the audited site's host, or a host with the same registered name (`acme` in acme.com, cdn.acme.com and acme.co.uk; under a shared hosting domain such as vercel.app, only the customer's own host and its subdomains), as the security module compares sites.

**Which image files are checked** (`checks/media/select.js`, `net/image-check.js`). Each check of a file costs requests, so at most `LIMITS.maxImageChecks` (50) distinct image URLs are checked per audit, chosen without randomness: the html pages in crawl order are gone through in rounds, each round taking the next not yet chosen `http(s)` URL of a rendered image from each page in document order, so the first image of every page comes before the second image of any. For a crawl of a site on this machine only images on the site's own origin are chosen. Nothing is requested from a site that stopped the crawl with a bot challenge or rate limiting, and when the site refused some of the crawl's page requests that way, no image on its own host is chosen (the notes and the report say so). The files are checked after the external link check of the `links` module has finished, never at the same time, so a host that serves both sees one request at a time. For each chosen URL, in order:

1. The robots.txt of its origin is read once per audit, with the rules of 4.2. Googlebot's and Googlebot-Image's access is evaluated from it without any request for the image. When it disallows the file for the crawler (`seekwide`), or could not be read, the file is not requested (outcome `disallowed` or `unverifiable`).
2. A `HEAD` request with `Accept: image/avif,image/webp,image/*;q=0.8,*/*;q=0.5`, so that a server that chooses the format by the `Accept` header (as image CDNs do, web.dev IMAGE_CDN) shows the best one it has. The user agent is the crawler's own, as for every request.
3. When the `HEAD` fails or answers 400 or above, or answers 2xx without a usable size, one `GET` with `Range: bytes=0-0` that reads at most 1 KiB; the size is the total of `Content-Range` (206) or `Content-Length` (200). No image is ever downloaded whole.
4. Redirects are followed by hand, at most 5, and each step is treated like a first request (its origin's robots.txt is read and obeyed). In a local audit a step to another origin is not requested.

Requests to one host are sequential, `1000 / rate_per_sec` of the crawl apart, and at least the crawl-delay of that host's robots.txt (capped at `LIMITS.crawlDelayMaxSec`); up to 4 hosts are checked at once. No new request starts after `LIMITS.imageCheckDeadlineMs` (90 s); the files not reached by then are `not_checked`. Outcomes: `ok` (the final answer is below 400), `broken` (404, 410 or `dns_error`), `unverifiable` (any other status or error, a robots.txt that could not be read, a refused step, too many redirects), `disallowed` and `not_checked`. Only `ok` and `broken` are units of the file checks, except `media.image.robots_blocked`, which needs only robots.txt. The audit records the files it chose (`run.image_files`: how many distinct images the pages show, how many were chosen, the count per outcome) and says in its notes and the report's scope how many of the chosen files answered.

Notes:

- **Text alternatives.** WCAG's failure F65 applies only when an image has none of `alt`, `aria-labelledby`, `aria-label` and `title`; the HTML standard also lets an image whose content the author cannot describe omit `alt` when it is the only content of a figure with a caption. `alt=""` is the documented markup for a decorative image (HTML, WAI's decorative images tutorial, MDN), so an empty `alt` is a choice and never fails. Google calls alt text the most important image metadata and shows an image without it as its first bad example (GOOGLE_IMAGES). A tracking pixel is not content; HTML asks for `alt=""` on such images, which the check does not require. A page built by a script framework can carry its templates in the HTML (`<img :src="item.image" :alt="item.title">`); the binding sets `alt` when the page renders, so it counts as a text alternative (the validation of 2026-11-12 found all 10 false findings of the first version there). A linked thumbnail with a caption (`<figure><a><img></a><figcaption>`, as wikis and galleries write it) counts as the figure's only content, a reading slightly wider than the HTML standard's bare case. Hiding counts only on the image itself: an image inside a hidden menu, tab, slide or dialog is shown when that opens and needs its `alt` then. Known gap: an `alt` that is present but says nothing useful in other ways (a keyword list, the page title on every image) needs judgment and is not measured.
- **File names and placeholders.** F30 lists `spacer`, `image`, `picture`, `picture 1`, `0001`, `Oct.jpg`, `Chart.jpg` and `sales\oct\top3.jpg` as text that is not an alternative; HTML asks generators not to use the file name as `alt`, and MDN's example of what not to write is `alt="image"`. The other placeholder words are of the same kind. A file name is compared only when it looks machine-made (a digit, `-` or `_`, no space), and as written, so `alt="Team"` on `team.jpg` and `alt="Coca-Cola"` on `coca-cola.svg` pass while `alt="IMG_0423"` on `IMG_0423.jpg` fails.
- **Dimensions.** web.dev (OPTIMIZE_CLS) asks for `width` and `height` on images so the browser reserves the space before the file arrives, and names CSS `aspect-ratio` as the alternative; Lighthouse does not warn when `aspect-ratio` is set. An image placed `absolute` or `fixed` by its inline style moves nothing around it. A style sheet can give an image, or the box around it, a fixed size, which the crawler does not read: in the validation of 2026-11-12 the first version (all rendered images, `low`) was right on 19 of 107 pages and wrong on 11 (utility classes such as `aspect-3/1`), and most of the rest were logos, icons and card thumbnails whose box the theme fixes. Leaving out the page's frame and reading utility classes removed every wrong one but one, and 19 of 55 stayed clearly worth a change; so the check is `info` and does not change the score.
- **Lazy loading.** web.dev says never to lazy-load the Largest Contentful Paint image and calls `fetchpriority="high"` together with `loading="lazy"` unnecessary. Which image is the largest one shown first needs layout: web.dev's own heuristic (the first featured image or first content image) is stated as unaware of the viewport. So the check does not guess; it finds the page contradicting itself, an image it marks as the most important (priority hint or preload) that it also tells the browser to load late.
- **Formats.** Google Search indexes BMP, GIF, JPEG, PNG, WebP, SVG and AVIF (GOOGLE_IMAGES), so no format keeps an image out of Search; the format check is about weight. Lighthouse's modern-format audit (LH_MODERN_FORMATS) covers JPEG, PNG and BMP and leaves out images whose saving would be under 8 KiB; web.dev puts WebP's saving at 25–35 %, so a file of 32 KiB or more is where 25 % reaches 8 KiB. GIF (animation), SVG (vector) and ICO are not units. A server can choose the format by the user agent instead of `Accept`, and the crawler never claims to be a browser, so such a server shows it a legacy format that browsers do not get; that and PNG kept for exact pixels are why it is `likely`. A server that says in `Vary` that its answer depends on `Accept` or `User-Agent` chooses the format per client: in the validation of 2026-11-12 an image CDN that said `Vary: Accept` answered JPEG even to `Accept: image/webp`, so browsers very likely get another format, and such files are not units. Evidence: `{observed: {content_type, bytes, vary}, expected, detail}`.
- **Size.** No official page gives a size limit for one image. Lighthouse flags pages whose requests add up to more than 5,000 KiB and suggests aiming under 1,600 KiB in all (LH_TOTAL_BYTES); 500 KiB, about a third of that for one file, is this plugin's rule of thumb, hence `info`. A file used only with `srcset` or `<picture>` sources is not a unit, because browsers load a candidate chosen for the screen, not necessarily this file. Known gap: an image much larger than the box it is shown in needs layout.
- **robots.txt and images.** Google's page on keeping images out of search (PREVENT_IMAGES) says the robots.txt of the host that serves the image decides, that a `Googlebot-Image` rule keeps images out of Google Images and a `Googlebot` rule keeps them out of every Google search. Googlebot-Image answers to the tokens `Googlebot-Image` and `Googlebot` (CRAWLERS: one matching token is enough), and Google's robots.txt rules apply only the most specific group that matches (ROBOTS_SPEC), which gives the fallback in the table. A site can keep its images out of Google Images on purpose, hence `likely`; the evidence names the crawler and the host whose robots.txt says so. Only the own site counts, because another organisation's robots.txt is not the owner's to change, and only images shown in a page's content, because logos, icons and badges in the frame are not what people look for in Google Images: in the validation of 2026-11-12 all 10 findings of the first version were a map host and a menu-photo host of other organisations that keep everything out, and a footer badge in a folder Wikipedia keeps out on purpose. robots-parser keeps no group for a `User-agent` line without rules, so such a group is read from the file's own `User-agent` lines; consecutive `User-agent` lines, blank lines between them or not, are one group.
- **Broken images.** A 404 or 410 image is shown to visitors as a broken image and is not indexed (HTTP_STATUS). A refusal (401, 403, 429), a server error or a timeout is `unverifiable`, as for external links: many image hosts refuse requests without a browser's referrer.
- **Captions.** WCAG 1.2.2 asks for captions on prerecorded audio in synchronized media, and its technique H95 tests that each video has a `<track kind="captions">`. A `subtitles` track carries dialogue only (H95, MDN; `kind` defaults to `subtitles`), so it does not pass. Captions burned into the picture (open captions) and captions that a player script loads (a streaming format's text tracks) are also sufficient (G93, G87) and cannot be seen in the HTML, and whether a video has speech at all cannot be told from the page: in the validation of 2026-11-12, 3 of the 4 videos reported were very likely silent (a demo clip, an animation, a silent film). So the check is `info`. Google's video documentation says nothing about captions; this check is about accessibility. A video loaded by a script is not seen at all.
- **Video structured data.** Google requires `name`, `thumbnailUrl` and `uploadDate` and says that without them it may be unable to extract any information about the video (VIDEO_STRUCTURED_DATA). `thumbnailUrl` counts when it is a non-empty string, an array with one, or an object with a `url` or `contentUrl`; `name` and `uploadDate` when they are non-empty strings. A `VideoObject` in microdata or RDFa is recorded (`video_markup`) but its properties are not checked.
- **No check for a video without structured data.** Google recommends video structured data and does not require it, and says that a video that only supplements a page (a blog post, a product page) does not make it a watch page, which is where video results come from (VIDEO_BEST_PRACTICES). Which page is a watch page cannot be told from its markup: the first version listed every indexable page with a video or a player of a known platform and no `VideoObject`, and all 15 findings of the validation of 2026-11-12 were pages where the video only supplements the content. The check was removed; extraction still records the players (`video_embeds`).
- **Not checked, and why.** An image sitemap is optional (IMAGE_SITEMAPS). File names that say nothing (`IMG00023.JPG`) are discouraged by Google but are not a failure of the page. Images in CSS backgrounds are not indexed by Google and are not read by the crawler. Images and videos that a script adds, and alt text quality beyond the patterns above, need rendering or judgment.

Rules without direct official support, kept on purpose and marked accordingly:

- `seo.content.thin`: Google states that it has no preferred word count. The check is `info`.
- `seo.h1.multiple`: no official rule limits a page to one `h1`. The check is `info`.
- `seo.canonical.missing`: Google recommends canonicals and does not require them. The check is `low` with weight 1.
- `seo.canonical.target_not_ok`: the documentation does not name this case; the finding is a measured fact (the canonical target does not answer 200, is not HTML, or is noindex).
- `links.depth.deep`: the page says Google uses the number of links needed to reach a page; the threshold of 4 is a rule of thumb. The check is `info`.
- `security.embeds.rare_host`: Google names scripts from an attacker's domain; a host used by one page only is a rule of thumb. The check is `info`.
- `security.content.spam_terms`: Google names pharmaceutical terms and counterfeit stores; the gambling terms and every topic word are this plugin's choice.
- `security.headers.*`: the rules come from MDN, the specifications and OWASP, not from Google; they protect visitors and do not affect ranking.
- `media.image.large_file`: no official page gives a size limit for one image; 500 KiB is a third of the total Lighthouse suggests for a page. The check is `info`.
- `media.image.legacy_format`: Lighthouse leaves out savings under 8 KiB; the 32 KiB floor applies web.dev's lowest WebP saving (25 %) to that number.
- `media.image.dimensions_missing`: web.dev documents missing sizes as a cause of layout shift, but whether a style sheet reserves the box cannot be seen without one. The check is `info`.
- `media.video.captions_missing`: whether a video has speech cannot be told from the page. The check is `info`.
- `media.image.alt_placeholder`: F30 names `spacer`, `image`, `picture`, numbers and file names; `photo`, `img`, `graphic`, `placeholder`, `untitled` and `alt text` are this plugin's additions of the same kind.
