Method

How the crawl works. Seekwide fetches pages one at a time at a limited rate, obeys robots.txt, and identifies itself with the user agent shown in the scope section. It reads the HTML the server sends and does not run JavaScript. When a site challenges or blocks it, it stops and does not try to get past the block.

What a finding is. Every finding comes from a scripted check that code ran on the crawled data, and the evidence is shown with it. Confirmed means the problem is a measured fact. Likely means a strong signal that can have a legitimate exception, so review it before acting.

How source files are found. The audit ran against the project's own local server. The address of each finding is matched to the file that answers it: by the routing rules of the Next.js App Router, or by its path for plain HTML. The file says where a fix belongs. Everything a finding reports was measured on the page the server sent, never read from the source code.

How security signals are found. The security checks read the same pages as the rest of the audit, with the same user agent: links and frames that the page's own markup hides, scripts and frames from other sites, spam terms, text in a writing system the site does not use, and the security headers of the start page. No other path is requested, nothing is tried against the site, and the crawler never pretends to be Google. Many hacks show their spam only to Google's crawler or to visitors who arrive from Google, so a clean result here does not prove that the site is clean; Search Console's Security issues report shows what Google found. Security headers protect visitors and are not Google ranking factors.

What an outside audit cannot see. Check these by hand: who has an admin account and whether each one is still needed; whether the files on the server match the versions you installed (core, plugins, themes); whether backups exist and can be restored; whether the software is up to date; and the Security issues and Manual actions reports in Search Console.

How images and videos are checked. The media checks read the <img> and <video> elements, embedded video players and JSON-LD of the crawled pages. Up to 50 of the image files the pages show are then checked, chosen page by page: the robots.txt of each image host is read first and obeyed, then each file gets a HEAD request that says AVIF and WebP are accepted, and a GET that reads at most 1 KiB when the HEAD says too little. No image is downloaded whole, so formats and sizes come from the server's headers. Images that scripts add, images in CSS backgrounds, and whether alt text describes the image well are not measured; neither are captions that are part of the picture or loaded by a player.

How scores work. A score is the weighted pass rate, from 0 to 100, of the checks that ran; 100 means no scored check found a failure. Coverage is the share of the module's checks that ran. Checks that did not run and informational checks do not change a score. The security module has two results: Security, a score for signs that the site was hacked, and Security headers, a count of the recommended response headers the start page sets (Strict-Transport-Security on https, nosniff and protection against framing), which protect visitors and say nothing about a hack.

What is not measured. The written summary and the suggestions, when present, are interpretation and never change a score. The layers marked "No data" were not measured at all.

Versions. Seekwide 0.1.1, rules 0.1.8. A different rules version can change findings without any change to the site.

Limits. This audit does not predict rankings or traffic. Fixing the findings removes obstacles and ambiguity for search engines; it does not guarantee any position, traffic or revenue.
