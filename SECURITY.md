# Security

## Reporting a vulnerability

Please report security problems privately through GitHub's "Report a vulnerability" button on the repository's Security tab. Do not open a public issue for them. You should get a first answer within a week.

Useful details: the version, what you did, what happened, and what you expected.

## What Seekwide is built to resist

Seekwide fetches pages from sites it does not control and hands the results to a model, so it treats everything it reads as untrusted.

- **Requests to private networks.** Every request goes through one function that refuses loopback, private, link-local and other non-public addresses. The check is made on the address the connection actually uses, and again on every redirect. A site on the user's machine can be crawled only when the crawl is started with `allow_localhost` for a loopback address, and then only that host and port are reachable: links, redirects and sitemaps that point at another local port are refused. The server enforces the one-origin rule; it cannot know who named the address (see the limits below).
- **Leaving the site.** The crawl stays on the site it was asked to audit: links, sitemaps and redirects that point to another host are recorded, not fetched. Five cases reach another host on purpose. If the start URL itself redirects to another host, that host becomes the audited site. If a robots.txt redirects to another host, it is read from there, as search engines do. The `links` module tests up to 50 external links, with one or two requests for the link and for each of at most 5 redirect steps, after reading the robots.txt of every site it contacts. The `media` module checks up to 50 image files that the crawled pages show, which can sit on another host such as a CDN: the robots.txt of every host first, then a `HEAD` request and at most one `GET` for the first byte that reads at most 1 KiB, for the file and for each of at most 5 redirect steps; no image is downloaded whole, no request starts after 90 seconds, and tracking pixels are never requested. The `smo` module checks up to 20 sharing images (`og:image`) the same way, except that each step gets one `GET` that reads at most the first 64 KiB, for the pixel size. And the `aso` module reads two files of the audited site itself, `/.well-known/apple-app-site-association` and `/.well-known/assetlinks.json`, after its robots.txt, at most 1 MiB each, following a redirect only where the crawl itself would go (the site's host, on its port). The `ai` module reads one more file of the audited site the same way, `/llms.txt`, at most 256 KiB, keeping only its title line, its number of links and its size; for a site on the user's machine only that origin is asked, through loopback for it alone. The two modules share one reader (`net/site-files.js`), so the file requests have one request path, through the same robots.txt cache, host gates and `guardFetch`. What robots.txt tells AI crawlers is read from the file the crawl fetched anyway: no AI vendor, search engine, IP list or vendor page is ever contacted during an audit, and the crawler never sends another product's user agent; the vendor data ships with the plugin. No request ever goes to Google Play or to a social platform, its short links or its image hosts, not even for robots.txt: such a link or image is left out and listed as not checked, by rule, a robots.txt or any other redirect that leads there is not followed, `safeFetch` itself refuses such an address, and a crawl is refused at such a start URL or stops when its start URL redirects there. Redirects are followed one step at a time, and robots.txt is checked before each step. Credentials inside a URL are removed before any request.
- **Instructions hidden in pages.** Page content is returned to the model as data inside structured fields, with a note saying so, and is clipped. The skills tell the model to treat it as material to audit. Nothing taken from a page is run as a command.
- **Text a person cannot see.** Control characters, direction overrides and Unicode tag characters are removed from page text when it is extracted and from every clipped value, so a page cannot hide words in a tool result or a report that a model reads and a person does not, or make a report read in another order. Every tool result that carries text from a page or from a saved `.seekwide/` file has a note that names it as data (`crawl_status`, `page_get`, `audit_run`, `findings_query`, `runs_list`, `runs_compare`, `fix_plan`, `project_detect`, and `profile_get` with a note of its own); its text fields are clipped, and URLs are at most 2048 characters long (a longer one in a saved run is cut there and ends in "…"). A tool's error message never quotes a value from a saved `.seekwide/` file or profile: it names the setting or field instead (`report.logo_path`, `repo.source_dir`), a URL from a saved run put into a sentence is cut at 200 characters, and the reason a crawl failed, which can quote an address the site chose, is clipped and given as data.
- **Markup in reports.** Every value written into the HTML report is escaped. Only `http` and `https` URLs become links. The report has no scripts and loads nothing from the network. In the Markdown report, page text cannot start an HTML tag, an image or a link of its own, and an e-mail address in it stays text.
- **Path tricks.** Project folders must be absolute paths, and run ids are checked against a strict pattern before they are used in a file path. A report logo is accepted only when its content really is a PNG, JPEG, WebP or SVG image, and a logo named by a project profile has to be inside the project folder, so a profile cannot pull another file into a report.
- **A project folder that reaches outside itself.** In repo mode the plugin reads the user's project to say which source file a finding comes from. The project folder is the boundary: the folder to read must be the project folder or lie inside it after symbolic links are resolved, symbolic links inside it are never followed or listed, a file is opened without following a link and checked again after opening, and a URL is matched against the list of the project's own files, so no path taken from a URL is ever opened. `node_modules` and dot folders are not read. Listings and file sizes are capped.
- **Code in the audited project.** Nothing in the project is imported, required or executed by the plugin's server: `package.json` is parsed as JSON, source files are known by name only, and HTML files are parsed as text. The server starts no process. The command that starts the project's local server is proposed by the model. The skills tell it to ask the user in the conversation and wait for a yes before running it, in every permission mode. The text of the project's `dev` script reaches the model as data, with a note saying so, together with its `pre` and `post` scripts (for example `predev`), which `npm run dev` runs as well; a script longer than shown is marked, so the question can say so.
- **Changing the project.** The plugin's server never changes a file of a project, with or without `/seekwide:fix`. It writes audit data into its own `.seekwide/` folder inside the project folder and into its crawl cache, and nothing else. A `.seekwide`, `runs` or run folder that is a symbolic link is refused, so a repository cannot point those writes elsewhere. The fix command is split in two: the server reads a saved run and the project's file names and says where a fix belongs, and the model makes the edit with Claude Code's own file tools. No tool accepts file content to write. The skill tells the model to show every change as a diff, to write only after a yes in the conversation, and never to commit.
- **Instructions in a fix plan.** A fix plan mixes the plugin's own instructions (`how`, `reason`, `notes`) with text from the audited pages (`current`, URLs) and names of the project's files. The instructions are fixed sentences; the only values put into them are the deployed address and line numbers the plugin counted itself. The deployed address is accepted only with a plain host name (letters, digits, hyphens and dots, an international name in its `xn--` form, or an IP address), whether it comes from `crawl_start`, `fix_plan` or a saved profile, so it cannot carry quotes, brackets or other code into the instructions or the suggested code; never a file name (a repository chooses its own) and never anything a page sent, not even the path of its URL. Files are named in fields of their own (`file`, `layouts`, `create`, `edit`), and a file to edit is named as the project's listing spells it. The deployed address is the one the user passed, or the `site_url` of the saved profile; a profile can arrive with a repository too, so the plan then says where the address came from (`site_url_source`) and tells the model to confirm it with the user before writing it. The saved run is treated as untrusted too, since a `.seekwide/` folder can arrive with someone else's repository: a finding's title is taken from the plugin's check definitions and not from the file, and a file name from it is passed on only when it is a plain relative path. The result's note names which fields are instructions and which are data. The plan carries a page's title, description, canonical and Open Graph tags, and none of its body text.
- **What the ai module stores.** The run's `ai` record holds no text from the site: the data date, the stated policy, statuses, crawler tokens with a boolean each, a count, and `/llms.txt`'s address with its outcome and status. Tokens are checked by form (letters, digits, `_` and `-`, at most 64 characters, at most 200 of them), not against the current crawler data, so a run saved before the data changed stays readable; a stored run whose `ai` record has any other form is refused as damaged, naming the field. Names a site writes in robots.txt (a `Content-Signal` name such as `constructor` or `__proto__`) are looked up in Maps, never on an object's prototype. A finding's evidence may quote a clipped robots.txt preference value or an llms.txt title, like any page text.
- **A `.seekwide/` folder written by someone else.** Before any tool uses a saved run, the values that tools put into their own sentences, file paths and keys are checked against the forms the plugin writes: finding ids, check ids and module names, every URL, line numbers, file names (relative paths inside the project without control characters), dates and versions. A run with any other form is refused as damaged, and the error names the field, never its value. Runs are listed in the order they were saved, not by their dates, so a planted run dated in the future is the newest only until the next audit is saved, and a run saved while this machine's clock was wrong is still read. A profile's errors name at most five unknown fields, each cut to 40 characters. Saved files are read without following a symbolic link, only when they are regular files, and only up to the largest size the plugin writes (20 MB for a run, 2 MB for the index, 1 MB for the profile); a folder on the way that is a link is refused. A run is checked against the same rules, its size included, before it is saved, so every run the plugin saves can be read back.
- **Calling something fixed that is not.** After a fix, a finding that is gone from the new audit counts as closed only when the check looked at the same page again, and only for the checks a fix exists for, whose units the plugin knows; for any other check a vanished finding is reported as not verified. A page that was not crawled, answers an error, or is no longer indexable is reported as not verified. Whether a check looks at one page or at the whole site comes from the plugin's own table, never from the saved finding, and a result's title and severity come from the plugin too. The new audit must be of the same address as the first, because findings are matched by address; a run of another address or port is refused, where otherwise every finding would look fixed.
- **Contacting the deployed site during a local audit.** A local crawl can be told where the project is deployed, so that canonical links, links and sitemap entries naming that address are read as pages of the local server. A crawl of a local site sends no request to any other address at all, whatever a redirect of its robots.txt, sitemap or pages says, so the deployed address is only compared against. When its robots.txt redirects to another address, the crawl stops as blocked and the result names the address it redirected to. The crawl and the link check are separate: `audit_run` checks up to 50 external links that the local pages name, from the user's machine, as for any audit; private and loopback targets are refused there too. The check of image files is not: for a local crawl it requests only images on the local site's own address, refuses every other origin itself (a redirect step and a robots.txt that redirects away included), and reaches loopback only for exactly that origin. Links and redirects to the deployed site are left out of the external link check by host, whatever their scheme or port, and only links on the exact origin are read as local pages; a redirect to the deployed site is not. When the address given matches nothing the pages name, the audit says so instead of claiming that it did. One path remains: an external site that the audited pages link to and that itself redirects to the deployed address is followed there by the link check, like any redirect. It is accepted only for a crawl of a site on the user's machine.
- **Naming the wrong project.** Source files are named only for a crawl of a site on the user's machine. A plain HTML file is named only when the page the server sent has the content of that file. The stored run and the reports hold paths relative to the project folder, never the folder's own path.
- **Oversized or endless responses.** Responses are limited in size, time and redirect count, also after decompression. What one page can contribute is capped as well (headings, links, images and the other lists), so a page built to be expensive cannot stall the server or fill the disk. A page that reaches a cap is named in the audit's notes, and the hidden-link scan reads every link of a page, keeping hosts rather than links, so padding a page cannot push a hidden link out of sight.
- **Input built to be slow.** One event loop serves every tool call, so the parts that read what a site sends are bounded in time and memory, not only in size: at most 200,000 tags of a page are parsed (the rest of such a page is not read, like the part of a body beyond the size limit), a URL longer than 2048 characters is treated as unusable, no pattern can backtrack on a long run of the same character, robots.txt is read by the plugin's own parser and its rules are evaluated in time linear in the URL (the ai module asks at most 200 pages for each counted AI crawler), its first 20 `Content-Usage` and `Content-Signal` values are clipped to 500 characters and read in one pass without backtracking, a compressed sitemap is unpacked to at most the 50 MB the protocol allows, at most 100 sitemap files are listed and elements nested more than 16 deep make a sitemap invalid. The link, image and hreflang lists of one page hold at most a million characters in all, and a crawl stops as truncated when its page records reach 150 million characters, so a site cannot exhaust memory or make its crawl too large to store. A site gets one crawl at a time, whatever scheme, port or `www.` the start address uses (on this machine, one per port), and at most three crawls run at once. Every request of a crawl, of the external link check and of the image check also passes one gate per host for the whole server: requests to a host go out one at a time, and one that follows another crawl's or audit's request to that host waits the host's delay. Parallel crawls and parallel audits therefore cannot multiply the rate a site sees. A robots.txt that one of them read for a public site is used by the others for ten minutes instead of being asked for again. A tool call's argument errors are reported for ten problems at most.
- **Imported search data.** An export from Search Console or Bing is a file the user supplies, and its text can be written by anyone: a search query, a filter value, a name inside an archive. It is untrusted input. The file must be a regular file inside the project folder, reached without a symbolic link, under the same rules as a logo named by the profile, and it is checked before it is opened. It may be at most 10 MB; a ZIP archive unpacks to at most 20 MB per entry and 40 MB in all, each entry to exactly the size and checksum it states, so a compression bomb stops at its stated size; ZIP64, encrypted and split archives are refused; an Excel file's XML may not declare a document type, so no entity is ever expanded; tables are capped at 50,000 rows, 64 columns and 4,096 characters a cell, and a file at 1,000,000 cells; a row of empty cells is not kept; every reader works in one pass over its input, the reading of XML tags, attributes and number formats included. Nothing in the file is evaluated: a cell that starts with `=`, `+`, `-` or `@` stays text, a formula is its stored value, and the report writes no spreadsheet, only escaped Markdown and HTML; in Markdown the filters and the file name are code spans, so an address in them is not turned into a link. A row with more cells than its header is refused rather than read with its columns shifted. Addresses are normalized, so only `http` and `https` pages are kept, and text is clipped with hidden characters removed. The file and the stored copy are never sent anywhere. Its text reaches the model only in data fields of a result that says the file is data, and error messages name a table, a row and a column, never a value. The stored copy in `.seekwide/imports/` is checked like a saved run before every use, since it can come with a repository: a value that does not have the form the plugin writes, a field the plugin does not write, or totals and a page order that do not agree with the rows make the plugin refuse the file, naming the field, never the value. The report labels the figures as data the user supplied, not measured by Seekwide; they order findings and change no check, finding or score.
- **Other users on the machine.** The crawl cache is readable only by the user who ran the audit.
- **Windows.** Windows has no flag that refuses a symbolic link when a file is opened, so every file read from `.seekwide/` and from the project is looked at first and refused when it is a link, on every system. A logo path from a project profile is checked against the project folder before the file is touched, and the way to it is walked without following a link, so neither a path such as `\\host\share\logo.png` nor a link in the project that points there makes Windows connect to another machine and offer the user's credentials. A profile logo reached through a symbolic link is refused on every system.
- **Monorepos.** At the root of a monorepo the plugin reads the workspace list of `package.json` or `pnpm-workspace.yaml` as text, in time linear in its length, and looks one level into the folders it names, inside the project folder, never into `node_modules` or a dot folder and without following a link, to say which of them are web projects. Lock files and `node_modules` of a web project in a subfolder are looked for up to the project folder and never above it.
- **Leaking the Google API key.** The key is optional. Claude Code stores it in the system's secure storage and hands it to the server in an environment variable. The server reads it in one place and sends it only to Google's PageSpeed Insights and Chrome UX Report APIs, over HTTPS, in a request header, so it is never part of a URL. Those requests follow no redirect, so the key cannot be passed on to another host. The key is not written to `.seekwide/`, to the crawl cache or to a log. No tool receives it: the tools are handed one function that has the key bound in, and of the server's environment only the report brand and logo settings. No tool result contains it, so the model never sees it. When Google refuses a request, the audit reports a fixed sentence of its own and not Google's message, which can name the key's Google Cloud project.
- **Telling Google about a private site.** Measuring Core Web Vitals sends the URLs of a few audited pages to Google (3 to 5, depending on the command, and never more than 10). A site on the user's own machine or on a private network address is never sent. The crawl records whether the site is local, and a crawl that does not say so is treated as local. A page whose address has a query string is never sent, because a query can carry a token or a personal value, and the host of each page is checked before it is sent: a local name (`localhost`, `.local`, `.internal`, `.lan`, `.home.arpa` and the like, with or without a trailing dot), a single-label name or an address that is not public is never sent, whatever the crawl file says about the site. When Google's test was redirected, the audit's note names only the host it ended on; the full address is kept in the run as data. For a public site whose URLs should stay private, `--no-cwv` turns the measurement off.

## What it does not protect against

- A model can still be misled by page content despite the precautions above. Review suggestions before acting on them.
- A logo set in the plugin settings, or passed to the report tool, can be any PNG, JPEG, WebP or SVG file of 200 KB or less that you can read, and it is embedded in the report. Only a logo named by a project profile is limited to the project folder. Look at a report before you send it.
- Seekwide does not sandbox Claude Code. The usual Claude Code permission prompts apply.
- Imported search data is shown as the export says it. Seekwide cannot tell a genuine export from one edited with care, and does not check the figures against Google or Bing. A hard link inside the project folder to a file elsewhere is read like any file there: a link check cannot tell it apart, and a git checkout cannot create one. Search queries in an export can be text that strangers chose by searching; this version stores and shows none of them, but a model that reads the file itself with its own tools reads them.
- The diff-and-approval step of `/seekwide:fix` is an instruction to the model, like the question before a dev server is started. The server cannot enforce it, because the server does not make the edit. In a session that lets Claude edit files without prompting, the model's question in the conversation is the only step between the plan and the change. Run it in a project under version control, and review the working tree before you commit.
- A fix is written by a model. It can be wrong in ways the audit does not measure: a title that misdescribes the page, a canonical that names the wrong address because the deployed address given was wrong. The second audit checks that the finding closed, not that the change is right for your site.
- Starting a project's dev server runs that project's code with your permissions, like running `npm run dev` yourself. The plugin's server never does it. Claude asks first and shows the command; say yes only for a project you trust. That question is an instruction to the model, not something the server can enforce: in a session that lets Claude run shell commands without prompting, the model's question is the only step between a request to audit and the command.
- For a Next.js project, Seekwide cannot check that the local server belongs to the project in the folder. If another project is being served on that address, findings name files of the wrong project. The audit says when no crawled page matches a route of the project.
- Another program running as the same user can read the environment of the server process, and with it the Google API key. Restrict the key in the Google Cloud console to the two APIs it is used for, so that a leaked key is of little use.
- Which address is crawled with `allow_localhost` is the model's choice. The server confines such a crawl to that one host and port, but it cannot tell an address the user named from one a page or a project suggested, and the audit commands let Claude call `crawl_start` without a permission prompt while they run. A crawl sends `GET` requests to that port for `/robots.txt`, the start URL, `/sitemap.xml` and the pages they link to, so any other service listening on `127.0.0.1` can receive them. Tell Claude which local address to audit.
- Python's static server, which Claude proposes for a plain HTML folder, serves every file in that folder, `.env` and `.git` included, to programs on this machine while it runs. Claude says so when it asks.
- Another program running as the same user that swaps files or folders in the project or in `.seekwide/` while the server reads them can get past the checks for symbolic links, which look before and after a file is opened but cannot lock it.
- In the Markdown report, a bare `http` or `https` address, or one that starts with `www.`, in page text can still become a link in a renderer that links addresses on its own, as it does in a GitHub comment. It is an address the audited site wrote; the HTML report never links one.

## Dependencies

The plugin has one runtime dependency, `parse5`, pinned, declared in `plugin/package.json` and locked in `plugin/package-lock.json`. The `plugin/` folder (the marketplace's `source`) is the only part of the repository that is installed: Claude Code copies it into its plugin cache and installs the dependency there. Adding the marketplace also clones the whole repository into Claude Code's marketplace folder, but the tests, fixtures, evals, docs and scripts in that clone are not part of the installed plugin and nothing runs them; the development tools CI installs are not installed at all. CI fails when `npm audit` reports a known vulnerability of any level in the dependency, and Dependabot proposes updates every week.

CI installs it with `npm ci --ignore-scripts` in `plugin/`, from that lockfile, which pins every package with its integrity hash. The GitHub Actions it uses are pinned to full commit SHAs, and the tools it installs (TypeScript, the Node.js types, Claude Code) to exact versions, so a moved tag or a new release cannot change what CI runs. The workflow's token can only read the repository, and the checkout does not keep it.

## Supported versions

Only the latest release gets fixes while the project is before version 1.0.
