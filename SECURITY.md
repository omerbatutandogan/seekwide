# Security

## Reporting a vulnerability

Please report security problems privately through GitHub's "Report a vulnerability" button on the repository's Security tab. Do not open a public issue for them. You should get a first answer within a week.

Useful details: the version, what you did, what happened, and what you expected.

## What Seekwide is built to resist

Seekwide fetches pages from sites it does not control and hands the results to a model, so it treats everything it reads as untrusted.

- **Requests to private networks.** Every request goes through one function that refuses loopback, private, link-local and other non-public addresses. The check is made on the address the connection actually uses, and again on every redirect. A local site can be audited only when its own address is the one the user named, and then only that host and port are reachable: links, redirects and sitemaps that point at another local port are refused. The server enforces this; it does not rely on the model.
- **Leaving the site.** The crawl stays on the site it was asked to audit: links, sitemaps and redirects that point to another host are recorded, not fetched. Three cases reach another host on purpose. If the start URL itself redirects to another host, that host becomes the audited site. If a robots.txt redirects to another host, it is read from there, as search engines do. And the `links` module tests up to 50 external links, with one or two requests for the link and for each of at most 5 redirect steps, after reading the robots.txt of every site it contacts. Redirects are followed one step at a time, and robots.txt is checked before each step. Credentials inside a URL are removed before any request.
- **Instructions hidden in pages.** Page content is returned to the model as data inside structured fields, with a note saying so, and is clipped. The skills tell the model to treat it as material to audit. Nothing taken from a page is run as a command.
- **Markup in reports.** Every value written into the HTML report is escaped. Only `http` and `https` URLs become links. The report has no scripts and loads nothing from the network.
- **Path tricks.** Project folders must be absolute paths, and run ids are checked against a strict pattern before they are used in a file path. A report logo is accepted only when its content really is a PNG, JPEG, WebP or SVG image, and a logo named by a project profile has to be inside the project folder, so a profile cannot pull another file into a report.
- **A project folder that reaches outside itself.** In repo mode the plugin reads the user's project to say which source file a finding comes from. The project folder is the boundary: the folder to read must be the project folder or lie inside it after symbolic links are resolved, symbolic links inside it are never followed or listed, a file is opened without following a link and checked again after opening, and a URL is matched against the list of the project's own files, so no path taken from a URL is ever opened. `node_modules` and dot folders are not read. Listings and file sizes are capped.
- **Code in the audited project.** Nothing in the project is imported, required or executed by the plugin's server: `package.json` is parsed as JSON, source files are known by name only, and HTML files are parsed as text. The server starts no process. The command that starts the project's local server is proposed by the model. The skills tell it to ask the user in the conversation and wait for a yes before running it, in every permission mode. The text of the project's `dev` script reaches the model as data, with a note saying so.
- **Changing the project.** The plugin's server never changes a file of a project, with or without `/seekwide:fix`. It writes audit data into its own `.seekwide/` folder inside the project folder and into its crawl cache, and nothing else. The fix command is split in two: the server reads a saved run and the project's file names and says where a fix belongs, and the model makes the edit with Claude Code's own file tools. No tool accepts file content to write. The skill tells the model to show every change as a diff, to write only after a yes in the conversation, and never to commit.
- **Instructions in a fix plan.** A fix plan mixes the plugin's own instructions (`how`, `reason`) with text from the audited pages (`current`, URLs). The instructions are fixed sentences; the only values put into them are the deployed address the user gave and file names from the project's own listing, never anything a page sent, not even the path of its URL. The saved run is treated as untrusted too, since a `.seekwide/` folder can arrive with someone else's repository: a finding's title is taken from the plugin's check definitions and not from the file, and a file name from it is passed on only when it is a plain relative path. The result says which fields are which. The plan carries a page's title, description, canonical and Open Graph tags, and none of its body text.
- **Calling something fixed that is not.** After a fix, a finding that is gone from the new audit counts as closed only when the check looked at the same page again, and only for the checks a fix exists for, whose units the plugin knows; for any other check a vanished finding is reported as not verified. A page that was not crawled, answers an error, or is no longer indexable is reported as not verified. The new audit must be of the same address as the first, because findings are matched by address; a run of another address or port is refused, where otherwise every finding would look fixed.
- **Contacting the deployed site during a local audit.** A local crawl can be told where the project is deployed, so that canonical links and sitemap entries naming that address are read as pages of the local server. A crawl of a local site sends no request to any other address at all, whatever a redirect of its robots.txt, sitemap or pages says, so the deployed address is only compared against. Links and redirects to the deployed site are left out of the external link check by host, whatever their scheme or port, and only the exact origin is read as local pages. When the address given matches nothing the pages name, the audit says so instead of claiming that it did. One path remains: an external site that the audited pages link to and that itself redirects to the deployed address is followed there by the link check, like any redirect. It is accepted only for a crawl of a site on the user's machine.
- **Naming the wrong project.** Source files are named only for a crawl of a site on the user's machine. A plain HTML file is named only when the page the server sent has the content of that file. The stored run and the reports hold paths relative to the project folder, never the folder's own path.
- **Oversized or endless responses.** Responses are limited in size, time and redirect count, also after decompression. What one page can contribute is capped as well (headings, links, images and the other lists), so a page built to be expensive cannot stall the server or fill the disk.
- **Other users on the machine.** The crawl cache is readable only by the user who ran the audit.
- **Leaking the Google API key.** The key is optional. Claude Code stores it in the system's secure storage and hands it to the server in an environment variable. The server reads it in one place and sends it only to Google's PageSpeed Insights and Chrome UX Report APIs, over HTTPS, in a request header, so it is never part of a URL. Those requests follow no redirect, so the key cannot be passed on to another host. The key is not written to `.seekwide/`, to the crawl cache or to a log. No tool receives it: the tools are handed one function that has the key bound in, and of the server's environment only the report brand and logo settings. No tool result contains it, so the model never sees it. When Google refuses a request, the audit reports a fixed sentence of its own and not Google's message, which can name the key's Google Cloud project.
- **Telling Google about a private site.** Measuring Core Web Vitals sends the URLs of a few audited pages to Google (3 to 5, depending on the command, and never more than 10). A site on the user's own machine or on a private network address is never sent. The crawl records whether the site is local, and a crawl that does not say so is treated as local. For a public site whose URLs should stay private, `--no-cwv` turns the measurement off.

## What it does not protect against

- A model can still be misled by page content despite the precautions above. Review suggestions before acting on them.
- A logo set in the plugin settings, or passed to the report tool, can be any PNG, JPEG, WebP or SVG file of 200 KB or less that you can read, and it is embedded in the report. Only a logo named by a project profile is limited to the project folder. Look at a report before you send it.
- Seekwide does not sandbox Claude Code. The usual Claude Code permission prompts apply.
- The diff-and-approval step of `/seekwide:fix` is an instruction to the model, like the question before a dev server is started. The server cannot enforce it, because the server does not make the edit. In a session that lets Claude edit files without prompting, the model's question in the conversation is the only step between the plan and the change. Run it in a project under version control, and review the working tree before you commit.
- A fix is written by a model. It can be wrong in ways the audit does not measure: a title that misdescribes the page, a canonical that names the wrong address because the deployed address given was wrong. The second audit checks that the finding closed, not that the change is right for your site.
- Starting a project's dev server runs that project's code with your permissions, like running `npm run dev` yourself. The plugin's server never does it. Claude asks first and shows the command; say yes only for a project you trust. That question is an instruction to the model, not something the server can enforce: in a session that lets Claude run shell commands without prompting, the model's question is the only step between a request to audit and the command.
- For a Next.js project, Seekwide cannot check that the local server belongs to the project in the folder. If another project is being served on that address, findings name files of the wrong project. The audit says when no crawled page matches a route of the project.
- Another program running as the same user can read the environment of the server process, and with it the Google API key. Restrict the key in the Google Cloud console to the two APIs it is used for, so that a leaked key is of little use.

## Dependencies

The plugin has two runtime dependencies, both pinned. CI fails when `npm audit` reports a known vulnerability in them, and Dependabot proposes updates every week.

## Supported versions

Only the latest release gets fixes while the project is in alpha.
