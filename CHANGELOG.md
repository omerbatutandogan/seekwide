# Changelog

Notable changes to Seekwide. Versions follow [semantic versioning](https://semver.org/); the rule set has its own version (`RULES_VERSION`) that changes whenever a check starts reporting something different.

## 0.1.0 (2026-11-12)

First release. Rule set 0.1.7: 77 checks, 62 of them scored, in four modules (`seo` with Core Web Vitals, `links`, `security`, `media`), plus repo mode and `/seekwide:fix`.

Every module was measured on about 20 real sites before this release, with a sample of its findings judged true, false or debatable by a judging agent, and a random fifth of those judged again, blind, by a second one. The sections below "Added" record what those measurements and the reviews changed before the release.

### Known limitations

- It does not run JavaScript; content that appears only after scripts run is not seen.
- The security module looks only at what the crawler is served. A hack that shows its spam only to Google's crawler is invisible to it, and none of its rules has been tried on a site that is actually hacked yet.
- A page that defines a React streaming runtime of its own can claim the exemption for React's hidden streaming blocks. Four mitigations were measured; none held without bringing back false alarms on Next.js sites.
- Core Web Vitals need a Google API key: without one Google refuses the lab test, and real-user data needs the key in any case.
- Repo mode supports Next.js App Router and plain HTML projects. Windows is covered by CI but has not been used by hand.

Rule set 0.1.1 differs from 0.1.0, which only unreleased builds used, in two ways: a module score is 99 at most when a scored check has a failure, and the `aria-label` of an element inside a link (an SVG logo, an icon, an image) counts as the link's text.

### Added

- A polite crawler: robots.txt, crawl-delay, one request at a time, XML sitemaps, template-aware sampling under a page budget, and a hard stop on bot challenges.
- 41 SEO checks, 6 Core Web Vitals checks and 10 link checks, all scripted, each with evidence, a confidence label and a documentation reference that was read when the rule was written.
- Repeatable scores per module, with coverage.
- Findings stored per run in `.seekwide/`, with stable ids so runs can be compared.
- Markdown and self-contained HTML reports, with optional agency name and logo.
- Commands: `/seekwide:basic`, `/seekwide:seo`, `/seekwide:links`, `/seekwide:all`, `/seekwide:report`, `/seekwide:setup`.
- Core Web Vitals in the `seo` module: six scripted checks, three on real-user data from the Chrome UX Report API (LCP, INP, CLS at the 75th percentile) and three on lab data from the PageSpeed Insights API (LCP, CLS, Total Blocking Time). The audit measures the start page and one page from each of the largest groups of similar pages (3 pages in a quick audit, 5 in a full one, at most 10), names them, and shows every value in both report formats.
- An optional `google_api_key` plugin setting, stored by Claude Code as a sensitive value. Without it the audit still completes: the Core Web Vitals checks are skipped with the reason, and coverage shows it. `--no-cwv` turns the measurement off.
- The "Experience" layer of the report is filled when real-user data was collected.
- Repo mode: audit the web project in the current folder and learn which source file each finding comes from. Audit commands run without a URL (or with `--repo`) detect the project, and Claude proposes the command that starts its local server; nothing starts without the user's approval, and the plugin's server starts nothing itself. Supported: Next.js with the App Router (page files, route handlers, route groups, dynamic and catch-all segments, metadata files such as `robots`, `sitemap` and `opengraph-image`, and `public/`) and plain HTML (with the line of the element). Other projects are named and audited by URL.
- A `project_detect` tool, and `source_dir` on `audit_run`. Findings carry `source {file, line, route}` where the file can be determined; it is in `findings_query`, in both report formats and in the run's `repo` summary. Finding ids do not depend on it.
- A canonical link that Next.js streams into the page body is reported by its own check, `seo.canonical.streamed_in_body`, with confidence `likely`, and no longer as a plain misplaced or missing canonical. Rule set 0.1.2 differs from 0.1.1 in this.
- `/seekwide:fix`: metadata fixes for the project in the current folder, from the findings of a saved repo-mode run. In scope: a missing or duplicate title or meta description, a missing canonical, missing Open Graph tags, and a missing sitemap with the robots.txt line that names it; in the `metadata` export or `generateMetadata` of a Next.js App Router page (and the `sitemap` and `robots` metadata files), or in the `<head>` of an HTML file. Every change is shown as a diff and written only after the user says yes; nothing is committed. Claude makes the edits with its own file tools; the plugin's server never writes into a project.
- A `fix_plan` tool: for each finding of a repo-mode run, whether a fix exists, the file and line, what the page sent, and how to change it. Findings that cannot be fixed safely are listed with the reason, and the rest are counted as out of scope.
- The re-audit after fixes: `verify_fixes` on `audit_run` says what became of each fixed finding (closed, still open, replaced by another finding of the same kind, or not verified because the check did not look at the page again), stores it in the new run, and both report formats show it in a "Fixes verified in this run" section.
- `site_url` on `crawl_start`, for a crawl of a local server: the address the project is deployed at. Canonical links, robots.txt `Sitemap:` lines and sitemap entries on that address are read as the same path on the local server, so a project that names its deployed URL is no longer audited as a site whose every page points elsewhere. A crawl of a local server now sends no request to any other address, also when its robots.txt or sitemap redirects away, and links to the deployed site are left out of the external link check. When the address matches nothing the pages name, the audit says so and names the address they use. The audit commands pass it in repo mode when it is known.
- Fixtures: a small Next.js App Router project and a plain HTML site, both with deliberate problems, under `fixtures/`.
- A `security` module and its command, `/seekwide:security`: ten scripted checks for signs, visible from outside, that a site was hacked or misused, and for the security headers of its start page. Links that the page's own markup hides from visitors or that sit on one punctuation character, to sites no visible link goes to; pharmaceutical, gambling and counterfeit spam terms on a site whose start page is about something else; pages in a writing system the site does not use; hidden frames from other sites; scripts and frames from a site no other page uses (informational); Strict-Transport-Security, `X-Content-Type-Options: nosniff`, clickjacking protection, Content-Security-Policy (informational) and a referrer policy that sends full addresses (informational). The module reads only the pages the crawl fetches and sends no request of its own. The header checks need the deployed site and are skipped for a server on this machine (a new capability, `live_site`). `/seekwide:all` runs the module; `/seekwide:basic` does not. Rule set 0.1.3 differs from 0.1.2 in these ten checks only.
- Page records carry the module's signals (`security`), read while a page is extracted. Records of crawls made before this version have none and are not units of the security checks.
- A report that includes the security module is titled after its modules (for example "SEO, link and security audit") and says in its method what the module can and cannot see from outside.
- Fixtures for the security module: a clean copy and a hacked copy of a small site, under `fixtures/security/`.
- Repo mode in a monorepo: `project_detect` at the root of a monorepo that is not a web project itself (npm, Yarn or Bun `workspaces`, or `pnpm-workspace.yaml`) lists the workspaces that are supported web projects under `workspace_projects`, and the skills ask which one to audit.
- Fixtures for Next.js 16 in TypeScript with `src/app`, `generateMetadata` and dynamic routes (`fixtures/next-ts`), and for an npm workspaces monorepo with the site in `apps/web` (`fixtures/monorepo`). Both were audited through the real server with Next.js 16.4.6 (`next dev`, and `next start` for the first), and every finding with a file named the right file and route.
- An eval suite for the skill flows under `evals/`, run with `claude plugin eval`: asking before a dev server starts and starting nothing on a no, starting, auditing and stopping it on a yes (also when the crawl fails), diffs before any edit in `/seekwide:fix` and the edits and re-audit after a yes, suggestions labelled as suggestions, a blocked crawl described as blocked, and security findings worded as signs.
- CI runs the tests on Linux, macOS and Windows, with Node.js 22 and 26.
- A `media` module and its command, `/seekwide:media`, also part of `/seekwide:all` (not of `/seekwide:basic`): ten scripted checks for images and video. From the markup of the crawled pages: images without alt text or another text alternative (an empty `alt` is a deliberate choice and passes; a script framework's `:alt` binding counts), alt text that is a file name or a placeholder, an image the page marks as its main one that is also lazy-loaded, `VideoObject` structured data without `name`, `thumbnailUrl` or `uploadDate`, and, as information, content images without width and height and videos that may have sound and have no captions track. From up to 50 image files per audit, with a `HEAD` request each after the robots.txt of their host and after the external link check: broken images, JPEG, PNG and BMP files of 32 KiB or more served although the request accepted WebP and AVIF, content images on the site's own domain whose host's robots.txt keeps them from Googlebot or Googlebot-Image, and files over 500 KiB (info). No image is downloaded whole; for a site on this machine only its own address is contacted, and a site that challenged or rate-limited the crawler gets no image request. Each rule names the official page it was read against on 2026-11-12, and the module was measured on 19 real sites before release: the rules that were often wrong or not worth acting on were narrowed or made informational, and a check for pages with a video and no `VideoObject` was dropped. Rule set 0.1.6 differs from 0.1.5 by these checks.
- `check_image_files` on `audit_run`; the run records how many images the pages show and how many files were checked (`image_files`), and both report formats show it with the module's score and method. Page records carry the fields the media checks need (each image's other text alternatives, hiding, tracking pixels, inline and utility-class sizes, whether it is in the page's frame, priority hint and preload, `<picture>` sources; `<video>` elements and their tracks; players of known video platforms; `VideoObject` in JSON-LD, microdata and RDFa).
- `loadRobots` answers for another crawler's product tokens too (`allowsAgents`), choosing the group of the most specific token that has one, else `*`, as Google does for Googlebot-Image; a group that names the crawler and has no rule allows it everything.

### Fixed

Rule set 0.1.4 differs from 0.1.3 in the first two of these.

- `links.anchor.uncrawlable` also reports a link whose `href` is a `vbscript:` or `data:` URL, and reads the scheme as browsers do (spaces and control characters around it, and tabs and line breaks inside it, are ignored, so a line break inside `javascript:` does not hide it). Google's crawlable-links page asks for an href that resolves to a web address its crawlers can request; neither scheme gives one. `mailto:`, `tel:` and other links to another program still pass.
- In a crawl of a local server that was told the deployed address (`site_url`), a link written with the full deployed address now leads to the same page on the local server, like canonical links and sitemap entries already did, so a page linked only that way is crawled and the link checks count such links as internal. The crawl still requests nothing outside the local server; a link to the deployed site in another scheme, host name or port, and a redirect to it, stay external and are left out of the external link check as before.
- Core Web Vitals are measured once per crawl and page count. The measurement is kept with the crawl, and every later audit of that crawl rates the same numbers, says that it reused them and when they were measured (`core_web_vitals.reused` and `measured_at`), and sends nothing to Google. A measurement in which Google returned nothing is not kept, and two audits of one crawl that run at the same time ask Google once.
- A deployed address written with a trailing dot (`https://example.com.`) is read without it, in `crawl_start` and in `fix_plan`, so it matches the pages and no fix writes the dot into a project.
- A Google API key that is set but cannot be sent (a space or a line break inside, a character outside plain ASCII, more than 256 characters) is reported as a key that cannot be used, and nothing is sent to Google; it was reported as no key, and PageSpeed Insights was asked without it.
- A crawl takes no new page after 30 minutes (`LIMITS.crawlMaxMs`); the page under way finishes. One that still has URLs to visit then ends as truncated with `time_limit_reached`, and the audit's notes, the report and run comparisons name the time limit instead of the page budget. The skip reason of the checks that need a complete crawl names every limit.
- The README no longer says that Claude Code installs the plugin's dependencies whenever it installs the plugin. Claude Code's documentation says it does so when it copies a plugin into its cache, from the lockfile, and not for a plugin it loads in place, which is what both install commands in the README do; the README now says to run `npm ci --ignore-scripts` first.
- A test that starts the server as a child process now fails at once when an assertion fails, instead of keeping the test run alive with the server still running.
- In a web project in a subfolder of the project folder (a monorepo workspace), the lock file and `node_modules` are also looked for in the folders above it, up to the project folder: the dependencies a workspace root holds were reported as not installed, so Claude proposed an install, and a pnpm, Yarn or Bun lock file at the root was missed, so the dev command was proposed with npm.
- A `package.json` that starts with a byte order mark, as Windows editors often write it, is read like any other; the project was treated as having none.
- On Windows the static server for a plain HTML folder is proposed as `python -m http.server`; `python3` is usually not installed there.
- `/seekwide:fix` reports the scores before the fix as well as after it: the skill now says that the base run's scores are in `runs_list`. In two eval runs Claude had given only the new scores.
- Tests that compared paths written for macOS and Linux, file modes, a file name with a line break, and a child process started without the variables Windows needs, now run on Windows too; three tests of POSIX file modes are skipped there. `.gitattributes` keeps line endings LF on every checkout.
- `docs/checks.md` escapes `<`, so element names in a check's description (`<iframe>`, `<img>`) show on GitHub instead of being read as HTML.

### Fixed after a validation on real sites

An audit of 20 real sites (Next.js, WordPress, Shopify, static documentation, a wiki, news, government, universities, small businesses, two Turkish sites) judged 923 findings: 1.6% were false and 46% accurate but not worth acting on. Rule set 0.1.5 differs from 0.1.4 in these:

- **No false hacking alarm on Next.js sites.** React's streaming server rendering sends a Suspense boundary's content later in the page inside `<div hidden id="S:n">` and moves it into place with an inline script as the page loads; on nextjs.org the whole footer arrives that way, and its links to other sites were reported as hidden links ("the site may have been hacked", security 75). A hidden element counts as revealed when the page has every part React writes, in order: the boundary's template before it, and an inline call of React's function, defined on the page, after it. Only its own `hidden` attribute is excused; `display: none` or an off-screen box inside or around it, or around the place the content is moved to, still counts, and the script must run the call as a top-level statement (not in a comment, a string or a block). The fallback such a boundary replaces no longer adds headings and text, so a page is not counted with two identical `h1` elements; its links stay, and its text still counts for spam terms.
- `og:image:url` and `og:image:secure_url` count as `og:image`, as the Open Graph protocol defines them.
- `links.internal.nofollow` reports a page only when every link to it on the page is nofollow, and only for a page the crawler could fetch: not the page itself, no query string (share, comment reply, cart and export links), allowed by robots.txt. Crawl results list the internal link targets robots.txt disallows (`disallowed_links`) for this.
- `links.anchor.uncrawlable` follows one rule: a link fails when what it opens is not in its href as a web address. A `javascript:` link that only prints, goes back or does nothing, on an element with no script handler, is a control and not counted; a script that may open a page, a `data:` URL, and a script that does nothing behind an `onclick` or another handler (`onmousedown`, `ng-click`, `@click`, a `data-href`) still fail. Page records keep `has_handler` for each link.
- `links.anchor.empty` and `links.anchor.generic` leave out links hidden from screen readers with `aria-hidden` and links to a place on the same page (`#`, `#id`), and pass a link when another link on the page to the same address is named (an image link beside the product's text link, "Read more" beside the article title). `links.anchor.generic` also passes a link with a descriptive `aria-label`. Page records keep `aria_hidden` for each link.
- `links.internal.redirect` reports a temporary redirect (302, 303, 307) as `likely`, with a sentence that the site can mean it (a login, a region, a cart), and leaves out a temporary redirect to a page that carries the link's own address, such as a login that sends the visitor back (`/login?next=%2Fdashboard`). A finding can now carry a lower confidence than its check.
- The report counts what the owner fixes: a group of link findings says how many distinct links on how many pages ("66 findings (3 links on 22 pages)") and shows each link once before repeating one; `audit_run`'s top groups carry `distinct_links` and `pages`.
- Three crawls started at the same moment all start; the third was refused while two existed.
- A crawl deleted from the cache (only the 20 newest are kept) is reported as deleted, with what to do, instead of as an unknown job id.
- `%7E` and `~` (and the other escapes of unreserved characters) are one URL, and robots.txt rules match either form. A canonical that differs from the page URL only in how `'`, `(`, `)`, `!` or `*` is written names the page itself, so a wiki page linked with an apostrophe is no longer left out of the checks as canonicalized elsewhere.
- The report of a crawl blocked before any page was read opens with that fact instead of "found no problems", and does not count checks that had nothing to look at. A start URL that redirects to a login or password page, and a start page with no links and almost no text (an empty JavaScript shell), get a note in the report and in `audit_run`. A sitemap the site refuses (401, 403, 429) is not reported as broken; the note and the skip reasons say it was refused. "1 other page has", not "have"; a canonical target that redirects is described by where it leads, not as a page that is not HTML.
- The security module has two scores: `security` for signs of a hack and `security_headers` for the start page's headers, which protect visitors and say nothing about a hack. A clean site with missing headers keeps a security score of 100.
- `security.embeds.rare_host` needs a crawl of 50 pages or more (on 25 pages every embed on one page is "rare") and leaves out the site's own host and its subdomains. A finding with a single hidden link says that it can be the site's own, such as a partner's logo in a block no longer shown, and the recommendation names that case before the hack.

### Fixed before the release

Rule set 0.1.7 differs from 0.1.6 in the first four of these.

- **Security headers are a count, not a score.** A site that sends none of the three scored headers got "Security headers 0/100" (example.com did), which reads as a verdict on the site. The result is now "0 of 3 recommended headers set" (2 on an http site, where Strict-Transport-Security does not apply): `security_headers` has `score: null`, a `count` (`passed` of `of`) and a note that says it in words, in `audit_run`, both report formats, the run index, the comparison of two runs and the skills. Runs stored earlier keep their score.
- **A spam link on another customer's host of a shared hosting service counts.** `security.hidden.external_link` treated every host under the same registered name as the site's own, so on acme.vercel.app a hidden link to spam.vercel.app, and on vercel.com one to any `*.vercel.app`, was never reported. Under the shared hosting domains of the Public Suffix List's private section (`vercel.app`, `netlify.app`, `github.io`, `myshopify.com`, `wixsite.com`, `blogspot.com`, `pages.dev`, `herokuapp.com` and 20 more), only the site's own host and its subdomains are its own. The media module compares image hosts the same way. The rule that makes acme.de the same organisation as acme.com stays: on the 205 saved validation pages it made no hidden link the site's own.
- **A link that names the site in its query is no longer a share link by that alone.** Any link whose query named the audited site was left out of `security.hidden.external_link`, so an injected `spam.test/pills?ref=acme.com` or `?u=https://acme.com/` hid. A share link now has to go to a known share or messaging service (Facebook, X, LinkedIn, Pinterest, WhatsApp, Telegram, Reddit, Tumblr, VK, Mastodon Share; the list and its sources are in `CHECKS-SPEC.md`) and name the site. On the 205 saved validation pages no finding was added or removed.
- React's streaming exemption is read as React writes it: only a `<div hidden>` or `<table hidden>` segment (React's table modes included, which were reported as hidden links), and only when the content lands in a place the page renders and no earlier element, SVG included, has the segment's id. A link that was itself the hidden element, or content moved into `<head>` or a video's fallback, took the exemption although no visitor sees it.
- A crawl of a local address where nothing answers (the dev server is not running, or listens on another port) ends as `failed` with "Nothing answered at http://127.0.0.1:3000 (…). Check that the dev server is running and that the port is right." It ended as blocked, with "robots.txt could not be read". A public site keeps that result.
- The gap through which a page can forge React's streaming runtime and keep a hidden block out of the hidden-link check is kept, and `CHECKS-SPEC.md` says why: each way of closing it that was measured either fell to one more statement of the forger's or brought the false alarms on nextjs.org and vercel.com back. The spam-term check reads such a block like the rest of the page, with its usual limits; a new test holds that.

### Security

The plugin's own security, reviewed area by area with a reproduction for every finding. None of these changes what a check reports.

- A page can no longer stall the server: a script of spaces no longer makes the Next.js data test take hours, at most 200,000 tags of a page are parsed, URLs longer than 2048 characters are treated as unusable, and robots.txt rules are evaluated in time linear in the URL (a 500 KiB file of wildcard rules and one long URL took minutes before). Sitemaps may nest at most 16 deep and at most 100 files are listed; the link, image and hreflang lists of one page hold at most a million characters, and a crawl stops as truncated when its page records reach 150 million characters.
- A `.seekwide/` folder that comes with someone else's repository can no longer redirect writes out of the project through a symbolic link, exhaust memory with an oversized file, put its own text into `fix_plan`'s instructions or error messages, or make its run the newest for good: such folders and files are refused, stored values that tools put into their own sentences are checked against the forms the plugin writes, and a run dated in the future is refused.
- `fix_plan` puts no file name into `how`; files are named in fields of their own, and the note says which fields are data. A deployed address taken from the saved profile is marked (`site_url_source`), and the fix command asks the user to confirm it. A re-audit takes a check's scope and a result's title from the plugin, never from the stored run.
- The question before a dev server is started shows the `pre` and `post` scripts that `npm run dev` runs too (`dev_server.also_runs`), and says when a script is longer than shown.
- Every tool result that carries text from a page or a saved file is labeled as data and clipped (`crawl_status`, `runs_list` and `profile_get` were not), and control characters, direction overrides and Unicode tag characters are removed from page text.
- When a local project's robots.txt redirects to another address, the blocked crawl names that address and says what to do.
- Pages whose address has a query string are never sent to Google, and each page's host is checked before it is sent.
- A site gets one crawl at a time, and at most three crawls run at once. Argument errors report ten problems at most. A response header named `__proto__` no longer breaks a crawl.
- `/seekwide:setup` no longer saves the profile without Claude Code's permission prompt; `/seekwide:basic`, `/seekwide:seo` and `/seekwide:links` say before the crawl which outside services are contacted.
- On Windows, which has no `O_NOFOLLOW`, a file in `.seekwide/` that is a symbolic link was followed when read. Every saved file is now looked at before it is opened and refused when it is a link, on every system.
- A logo path in a project profile is checked against the project folder before the file is touched, and the way to it is walked without following a link. On Windows, opening a path such as `\\host\share\logo.png`, or a link that points there, connects to that machine and offers the user's credentials; such a path was refused only after it had been opened. A profile logo reached through a symbolic link is now refused on every system, also when the link stays inside the project.
- CI: GitHub Actions pinned to commit SHAs, Claude Code and the Node.js types pinned to exact versions, install scripts not run, and the checkout does not keep the token.
